## TL;DR
Yogendra Miraje shares lessons from building skill-centric agentic products at FactSet, arguing that skills are the new features in AI-driven products and that engineers' roles are shifting from shipping features to shipping harnesses. He covers the mechanics of adding skill support, practical learnings about descriptions and evals, and the governance needed to scale skill libraries in the enterprise.

## Key Takeaways
- **Skills are the new features.** In agentic products, business logic that used to live in screens and buttons now lives in skills.
- **The engineer's role is shifting** from shipping features to shipping harnesses—smooth vehicles for skills to run in.
- **A minimal skill harness** needs only a skill registry, a system prompt, and a file-read tool (plus bash or a sandbox if scripts are involved).
- **Descriptions are routing signals.** They should be aligned to user intent, kept distinct, and never allowed to go stale.
- **Skills are contracts versioned to a model**, not documentation—always rerun evals when upgrading models.
- **Cut skills by user intent, not by data model.** Narrow use cases are a fine starting point; refactor as real use cases emerge.
- **Progressive disclosure** means the agent sees only name, description, and path in the system prompt, then reads full skill bodies only when needed.
- **Scaling changes the routing mechanism itself**—from system-prompt stuffing, to embeddings/similarity search, to hierarchical metadata-filtered governance.
- **Skill library governance is non-negotiable at enterprise scale**, covering admission, ownership, boundaries, lifecycle, and coherence.
- **Borrow proven coding practices**—PR-style reviews, code owners, semantic versioning, deprecation warnings, change logs—for skill management.

## Detailed Breakdown

### Introduction and Context [00:01](https://www.youtube.com/watch?v=7jjudsEhBtM&t=1s)
Yogendra ("Yogi") Miraje introduces himself as a principal AI engineer at FactSet, a financial data and research company. He references his talk from the previous year's conference about "blueprints"—a simple set of steps handed to agents so they wouldn't have to discover their path each time. In retrospect, blueprints were a naive form of skills. Since Anthropic open-sourced skills in October, FactSet moved away from maintaining its own blueprint standard and fully adopted skills.

### Audience Check and Scope [02:06](https://www.youtube.com/watch?v=7jjudsEhBtM&t=126s)
Yogi asks the audience how many build skills—nearly everyone raises a hand. He then asks how many have built skills only in the context of coding agents like Claude Code or Codex, versus those who have built their own harness with skills. Most online discourse focuses on coding-agent skills, but this talk targets skills in the context of agentic products: how to add skill support to your own harness and scale it at enterprise level.

### Skills Are the New Features [02:37](https://www.youtube.com/watch?v=7jjudsEhBtM&t=157s)
Traditionally, products were surfaces of screens, buttons, forms, and dashboards. Now agents are at the forefront—users talk to agents or agents navigate the product behind the scenes. If the agent becomes the main interface, where do features live? Yogi frames it as: prompts define **who** the agent is, tools define **what** it connects to, and skills define **how** a task gets done. Skills are the place for business logic. Equity research and wealth management workflows that used to be buttons and dropdowns are now merely skills.

### The Engineer's Shifting Role [04:40](https://www.youtube.com/watch?v=7jjudsEhBtM&t=280s)
Because skills can be authored by anyone with good product understanding, the engineer's role shifts from shipping features to shipping harnesses—smooth vehicles for skills to run in.

### What Is a Skill? [05:12](https://www.youtube.com/watch?v=7jjudsEhBtM&t=312s)
A skill is a standardized way to teach AI agents how to do a specific task well. The model can function without a skill but performs better with one. A simple skill may be just markdown; a complex one can reference multiple files and executable scripts. The `skill.md` file is the heart of the skill: name and description in the front matter enable discovery, while the body holds business logic, instructions, and references to files and scripts.

### Minimal Harness Requirements [06:14](https://www.youtube.com/watch?v=7jjudsEhBtM&t=374s)
To add bare-minimum skill support, you need three things: a skill registry, a system prompt, and a basic file-read tool. If running scripts, add bash or a code sandbox. A skill registry is simply a collection of skills with name, description, and path. Yogi introduces three example skills: company research (web search producing markdown), report HTML (markdown to HTML), and report PDF (markdown to PDF).

### Skill Discovery and Progressive Disclosure [07:17](https://www.youtube.com/watch?v=7jjudsEhBtM&t=437s)
Discovery works by concatenating name, description, and path into the system prompt—deliberately excluding the skill body. This is progressive disclosure: the agent reads available skills and only loads the full body of the ones it decides to use. The agentic loop tracks messages, calls the model with messages and agent tools, appends tool calls, and ends when there are no more tool calls. In the example, asking to "publish a report of NVDA" triggers company research, then the build-report skill to produce HTML output.

### Descriptions as Routing Signals [09:23](https://www.youtube.com/watch?v=7jjudsEhBtM&t=563s)
Descriptions are the routing signals that determine which skill the agent picks. Yogi demonstrates with the report HTML and report PDF skills: the PDF skill description says "use the skill only when user asks for a PDF report"—the word "PDF" is the trigger. Descriptions should be aligned to user requests rather than the skill itself, kept distinct enough to avoid confusion, and never allowed to go stale. In agentic products, most skills are model-driven—non-technical users shouldn't bear the cognitive load of tracking skills manually.

### Cut by User Intent, Not by Data Model [10:29](https://www.youtube.com/watch?v=7jjudsEhBtM&t=629s)
Yogi initially built skills around narrow data-model-aligned use cases (estimation analysis, fundamentals). Real use cases didn't match the data model, forcing multiple refactors—which is fine. In practice, an "estimate analysis skill" should become an "earnings preparation skill," and separate "news" and "analyst rating" skills should become a "pre-market briefing skill."

### Skills Are Contracts, Not Documentation [11:32](https://www.youtube.com/watch?v=7jjudsEhBtM&t=692s)
After upgrading to a new model, agents stopped obeying skills even though no skill lines changed. The new model focused on the beginning of each skill, while critical instructions sat at the end. Skills are contracts versioned to a model—not documentation. Always rerun evals when upgrading models; skills without evals are "wishful thinking."

### Scaling the Routing Mechanism [13:08](https://www.youtube.com/watch?v=7jjudsEhBtM&t=788s)
Shoving skills into the system prompt works for a few skills but falls apart past ~10. Options include embeddings with similarity search or a smaller model to shortlist skills for the system prompt. At hundreds of skills, you need hierarchy, metadata filters, and governance to keep the library searchable and coherent.

### Skill Library Governance [13:40](https://www.youtube.com/watch?v=7jjudsEhBtM&t=820s)
Yogi outlines five governance aspects: **admission** (should this skill exist or merge into an existing one?), **ownership** (named maintainers like code owners), **boundaries** (allow-listed tools and access control), **lifecycle** (semantic versioning, deprecation warnings, change logs), and **coherence** (periodic audits and validation checks). Governance doesn't have to be red tape—it can be automated with human-in-the-loop, borrowing decades-proven coding practices like PR reviews.

### Closing Takeaways [16:20](https://www.youtube.com/watch?v=7jjudsEhBtM&t=980s)
Skills are the features in agentic products. Engineers shift from shipping features to shipping harnesses. The routing mechanism doesn't just get tuned as you scale—it changes entirely. At enterprise scale, skill library governance is non-negotiable.
