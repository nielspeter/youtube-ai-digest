## TL;DR
Jason Lopatecki, founder of Arize, presents "Signal," an in-product agent designed to bridge the gap between observability data and automated code fixes. By moving observability from a human-clicking paradigm to an agent-driven loop powered by well-designed skills, traces, and online evals, teams can get a "cold start" on issues with pre-gathered evidence and proposed fixes, shifting their role from responder to reviewer.

## Key Takeaways
- **Observability is shifting from human-centric to agent-centric.** Traditional observability relies on humans clicking through UIs and graphs; the future involves agents autonomously using telemetry to debug and fix software.
- **The bottleneck has moved from the fix to confidence.** With coding agents, generating a fix is no longer the primary bottleneck—the challenge is having enough evidence and confidence to know the fix is correct and safe to push.
- **Inverting the debugging loop.** Instead of humans grabbing tickets and investigating from scratch, agents can analyze errors and present humans with pre-gathered evidence and a "cold start" on the issue.
- **Tracing and logging must increase by orders of magnitude.** Because agents can dig through massive amounts of data (unlike humans who find it noisy), systems should log and trace 10x more to clearly show the exact code path taken.
- **Skills are the magic ingredient.** The power of an agent comes from well-designed skills that pull the right observability data (traces, logs) into temporary files within the repo, giving the coding agent the context it needs.
- **Moving from local to sandboxed environments.** Developers should take their local debugging setups (using tools like Claude Code or Cursor) and run them periodically in secure sandboxes triggered by events or schedules.
- **Evals act as a continuous AI assessment layer.** Online evals (LLM-as-a-judge) are layered on top of production traces, allowing the agent to catch specific, known failures or safety issues at scale.
- **Security and VPC deployment matter.** Many enterprise customers (like Uber and Booking.com) require agents to run inside their VPC so production database connections aren't sent to external cloud providers.
- **The system is open and composable.** Users can choose their harness (Claude Code), sandbox (Arize, Daytona), and skills, and can even resume cloud agent sessions locally if they want to take over the debugging.

## Detailed Breakdown

### The Evolution of Observability [00:35](https://www.youtube.com/watch?v=9HbzAWnKbo4&t=35s)
Jason introduces his background as a builder and founder of Arize, detailing their experience building an in-product agent named Alex. He explains that observability used to be a UI for humans to click through, but it is now shifting to a 2.0 model where coding agents use telemetry (the "smoke thrown off by your system") to understand code paths and debug software autonomously.

### The Self-Improving Agent Loop [03:10](https://www.youtube.com/watch?v=9HbzAWnKbo4&t=190s)
The ultimate goal is building systems that autonomously fix themselves. Jason notes that while we can now build at "agent speed," improving systems at that speed is still a bottleneck. The challenge is no longer generating the fix, but having the confidence that the fix is right. He introduces the idea of inverting the loop: instead of humans grabbing tickets and investigating, agents analyze data first and present humans with deep evidence, shifting the human's role from responder to reviewer.

### The Anatomy of an Agent Fix [05:15](https://www.youtube.com/watch?v=9HbzAWnKbo4&t=315s)
A self-improving loop is driven by triggers (periodic or event-based) and context (driven by skills). Skills connect to observability platforms to gather context, pulling production logs and traces down into temporary files within the code repo. This combination of the actual code path and the observability data in the repo is what gives the agent the magic ability to formulate a fix. Jason emphasizes that we need to trace and log 10x more than we do today because agents can parse this noise to understand exact system paths.

### Product Demo: Signal and Sandboxes [10:30](https://www.youtube.com/watch?v=9HbzAWnKbo4&t=630s)
Jason demonstrates Arize's products: AX (their SaaS platform, which can also be deployed in a VPC), Phoenix (open source), and Signal (their new agent running in AX). Using a financial trading agent as an example, he shows how Signal periodically runs, identifies issues (like missing guardrails or safety issues), and can push these to GitHub. He highlights the flexibility of the platform: users can pick their harness (like Claude Code), choose their sandbox (Arize, Daytona, or cloud-managed), and customize prompts and skills.

### Q&A: Connecting Claude Code Directly to Data [16:20](https://www.youtube.com/watch?v=9HbzAWnKbo4&t=980s)
An audience member asks why Claude Code can't just be connected directly to the data to do all this. Jason responds that while that is the vision, it requires well-designed skills to work well. You can't just point an agent at raw data; the skill needs to find the right traces, format them into files (sometimes 10MB), and place them in the repo so the agent can work its magic compositely.

### Q&A: The Role of Evals in the Loop [17:52](https://www.youtube.com/watch?v=9HbzAWnKbo4&t=1072s)
When asked where evals fit into the process, Jason explains that evals (specifically online evals using LLM-as-a-judge) are layered on top of production traces. They act as a pre-processed AI assessment that runs continuously. If a specific failure is found, an evaluator can be created to catch it next time. Signal then uses both the raw trace data and this layered eval data to understand and fix issues.
