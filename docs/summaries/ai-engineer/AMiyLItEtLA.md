## TL;DR
Vaibhav Gupta shares how his team builds a programming language (BAML/Bemo) with no code reviews, no AI standardization, and heavy parallel work by "fighting slop with slop"—using AI-generated tools, agents, and first-principles language design to manage codebases humans no longer fully read. He argues that foundational layers like TypeScript and JavaScript carry baked-in "slop" designed for human productivity, and that agent-first languages, tooling, and processes are needed to ship reliable software at agent speed.

## Key Takeaways
- "Slop" is simply any code you don't read—and it will only grow as AI-assisted development accelerates.
- Instead of mandating one AI tool, the team uses a minimal, model-agnostic `architecture.md` file containing only long-lived invariants (e.g., compiler layers).
- Design docs must be high quality: "code can be slop, writing cannot." A custom design-doc tool with Slack notifications and mandatory peer review enforces this.
- A dependency-graph visualizer plus CLI-based invariant checks prevent agents from introducing leaky architecture; the architecture hasn't changed in months.
- Continuously running agents generate BAML programs from scratch; other agents inspect transcripts to find inefficiencies (e.g., three tool calls where one would suffice), enabling data-driven, A/B-tested language improvements without writing code.
- TypeScript and JavaScript contain "slop baked into the language" (e.g., string coercion in sorting, type quirks) because they were designed for human productivity, not agent productivity.
- BAML offers agent-first features: visual code navigation, zero-cost execution traces, inferred error types with exhaustive handling guarantees, and every function automatically exposed as a CLI command.
- BAML functions are callable from Python, TypeScript, Rust, Go, Ruby, Java, etc., with full type safety—lambdas, generics, and closures cross language boundaries seamlessly.
- Traditional processes (code reviews, CI/CD adoption) must evolve; teams that resist process change will be outpaced by those who embrace agent-speed workflows.
- Vaibhav calls for new foundational systems: a new Git, a new database, and a new programming language designed from first principles for an AI-first world.

## Detailed Breakdown

### Introduction and Provocative Engineering Practices [00:01](https://www.youtube.com/watch?v=AMiyLItEtLA&t=1s)
Vaibhav opens by stating his team does no code reviews, requires every engineer to work in parallel, and has no standardization on AI tooling. Anticipating the audience's assumption that this is a reckless young YC startup, he clarifies he is a millennial and that the team has spent three years building a programming language—a domain with zero tolerance for slop or bad design decisions.

### Defining Slop and the Mentor's Lesson [01:03](https://www.youtube.com/watch?v=AMiyLItEtLA&t=63s)
He defines slop as "any code you don't read" and warns the audience that this moment represents the least amount of slop their codebase will ever contain. He recounts meeting his mentor, "Slop Sue," who taught him: "to defeat the slop, we must become the slop."

### The Skirmish of Standards: architecture.md [02:06](https://www.youtube.com/watch?v=AMiyLItEtLA&t=126s)
Rather than forcing engineers to use a specific AI tool (Claude, Codex, or whatever is trending on Hacker News), the team created an `architecture.md` file instead of a `Claude.md`. It is deliberately small, contains only things that will not change for months or years (e.g., compiler layers), and instructs agents to consult at least one other person, slowing them down slightly for safety.

### The Battle of Design: Design Doc Tooling and Slack Integration [02:36](https://www.youtube.com/watch?v=AMiyLItEtLA&t=156s)
The team's rule: "code can be slop, writing cannot." They built a design-doc tool replacing Notion and GitHub for design docs, with versioning and commenting. Adoption lagged until they added a Slack integration that notified a channel on every update. The channel became the company's most popular; people read docs at 2 a.m. Docs are backed by Markdown files and CLI scripts so agents can interact with them. When Vaibhav began shipping ten design docs a day, the team pushed back, leading to a rule requiring authors to ensure people actually read their docs—driving quality up.

### The Battle of Architecture: Dependency Graph Visualization [04:10](https://www.youtube.com/watch?v=AMiyLItEtLA&t=250s)
They built a tool that visualizes the internal dependency graph with semantic boundaries and package-level views. CLI tools guarantee certain invariants cannot be broken. When Claude (or any agent) adds a leaky dependency or new package, CI/CD or Git history pinpoints the break. This approach stabilized their architecture for three to four months.

### The Battle of Code: Agent-Generated BAML Programs and A/B Testing [04:40](https://www.youtube.com/watch?v=AMiyLItEtLA&t=280s)
Vaibhav asks whether anyone would ship a programming language without reading the code, noting Python still has bugs 25 years later. Their solution: agents constantly generate BAML programs from scratch. They inspect full Claude transcripts—both humans and other agents—to find what was good, bad, inefficient (e.g., three tool calls where one would suffice), or tasteless. Agents then propose fixes. Crucially, they can A/B test language features by measuring tool-call counts, error rates, and correctness deterministically—building data-driven systems without writing code. He emphasizes that building a programming language traditionally required hundreds of thousands of man-hours and still produced broken systems; now millions of tokens can make it stable.

### The War Is Still Lost: Foundational Slop in TypeScript and JavaScript [07:16](https://www.youtube.com/watch?v=AMiyLItEtLA&t=436s)
Despite winning battles against slop, Vaibhav believes the war will be lost because foundational tools are themselves broken. TypeScript's design goal balances correctness and productivity—but productivity means *human* productivity. He demonstrates TypeScript quirks (string coercion in sorting, unexpected type behaviors) as "slop baked into the language." He traces the lineage: JavaScript existed, then CoffeeScript, then TypeScript, then attempts to add facts—but the foundation underneath is already broken. He asks why we keep patching instead of trying something different.

### BAML: Visual Code Navigation and Opt-In Reading [09:20](https://www.youtube.com/watch?v=AMiyLItEtLA&t=560s)
He presents a new way to think about code: instead of reading raw source, a visualization tool lets you click through code, expanding and zooming into semantic boundaries. You can opt into which parts to read and ignore the rest as "slop." While a pipeline runs, you can expand nodes to inspect only what matters.

### Zero-Cost Execution Traces for Humans and Agents [10:21](https://www.youtube.com/watch?v=AMiyLItEtLA&t=621s)
In a world where humans don't read all code, execution traces become the primary way to understand a program. BAML provides full traces showing time spent in each part. Unlike Python or TypeScript, where tracing everything is untenably slow, BAML makes this effectively zero-cost because it is built for agents from the start. Every file has a tracing system Claude can navigate to find bugs, errors, and inefficiencies and optimize code autonomously.

### Agent-First Tooling: Beyond grep and Ripgrep [11:54](https://www.youtube.com/watch?v=AMiyLItEtLA&t=714s)
Vaibhav contrasts traditional `grep` and `ripgrep` with agent-first search. Instead of grepping for "calculate" and getting raw matches, you can ask the tool to describe a function, return docstrings, source code, and all usage sites in a single tool call. External libraries can be queried the same way—no web search needed. "The code is always the source of truth; docs may lie, but code cannot."

### Every Function as a CLI Command [13:27](https://www.youtube.com/watch?v=AMiyLItEtLA&t=807s)
Every BAML function is immediately available as a standalone CLI command with typed parameters. Functions like `add` or `multiply` can be bundled into a single CLI binary, runnable without executing the full program. Everything is type-safe, deterministic, and guessable. Agents don't need to grep; they can target any architecture (Windows, Mac, Linux, WASM) without deployment worries, letting engineers move at agent speed.

### First-Principles Error Handling [15:01](https://www.youtube.com/watch?v=AMiyLItEtLA&t=901s)
He contrasts BAML's error handling with the agent pattern of nesting try/catch blocks and eventually giving up with `console.log`. In BAML, `divide` throws a division-by-zero error, and the function *knows* it throws that error without the developer writing anything. Calling functions infer the error types transitively. The compiler can prove exhaustive handling—if you want an API that never throws, the system verifies constraints. Catching an error and returning a sentinel value updates the type signature so the function is guaranteed not to throw that error. "Code is a matter of trust; we don't use ML code blindly because we don't trust it yet."

### Cross-Language Interop Without Rewrites [17:35](https://www.youtube.com/watch?v=AMiyLItEtLA&t=1055s)
Acknowledging that asking everyone to rewrite code in a new language is unrealistic, he shows BAML functions callable from Python, TypeScript, Rust, Go, Ruby, Java, and future languages—with full type safety. Functions get both sync and async variants. Lambdas, generics, and closures can pass across language boundaries. The type system "never lies" and becomes the center of truth preventing invariants from entering the codebase.

### Closing: Evolve Processes and Rebuild Foundations [19:38](https://www.youtube.com/watch?v=AMiyLItEtLA&t=1178s)
Vaibhav reiterates that complex systems can be built without code reviews, with parallel work, and with unstandardized AI use—provided the team is thoughtful about underlying systems. He cites an engineer who built a partial C compiler purely in BAML. He compares adopting new processes to companies that initially resisted CI/CD: they slow down for three months but then move much faster. He urges the audience to embrace slop, build "sloppy tools" to make systems robust, and for the bravest, to rethink foundational layers—new Git, new database, new programming language. He closes: "I'm Vaibhav, and I work on Bemo."
