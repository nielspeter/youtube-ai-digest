## TL;DR
Rajat Shah, a staff software engineer at Netflix, presents a practitioner's playbook for introducing AI agents into performance engineering to reduce infrastructure costs and ship code faster. By feeding well-structured profiling data to LLM coding agents, teams can automate the identification and fixing of suboptimal code patterns. Shah outlines a maturity model that starts with reactive profiling analysis and shifts left toward proactive code authoring, emphasizing that strong foundational engineering practices—like test coverage and canary deployments—must precede AI autonomy.

## Key Takeaways
- **The Problem:** AI coding agents ship code 10x faster but don't always write optimally performant code, leading to increased compute costs and manual performance bottlenecks.
- **Profiling Data is Universal:** Regardless of the programming language (Java, Python, Go), profiler outputs (call stacks, CPU time) are well-structured and easily digestible by LLMs.
- **Pattern Recognition:** LLMs are already trained on public codebases and can easily recognize common anti-patterns (e.g., O(N²) loops, unnecessary object allocation) directly from profiling data without needing to see the codebase first.
- **End-to-End Automation:** An AI agent can identify a bottleneck, clone the Git repo at the exact production commit, trace the code path, and submit a code review in under 5 minutes.
- **Cross-Repo Scaling:** Once an AI agent identifies an anti-pattern, it can search across multiple code repositories to find and fix the same inefficient pattern across an entire organization.
- **Stateful Memory via Catalogs:** A centralized, human-and-machine-readable Git repo containing markdown files of patterns and anti-patterns acts as long-term memory for stateless LLMs.
- **Human-in-the-Loop is Required:** Because optimizing code running in production is risky, AI agents should propose code reviews for human approval rather than pushing changes directly to production.
- **Canary Deployments Provide Ground Truth:** While profilers give estimates, canary deployments (comparing old code vs. new code under live traffic) provide the ground truth needed to validate a fix before human review.
- **Shift Left:** Start reactively by fixing production code, then gradually move proactive checks earlier into the code review phase and ultimately into the code authoring phase to prevent inefficiencies from being written in the first place.
- **Foundations Before AI:** Test coverage, canary automation, and security guardrails must be rock-solid before introducing AI agents; otherwise, automation will just create more friction and production bugs.

## Detailed Breakdown

### The Problem with Performance Engineering [00:00](https://www.youtube.com/watch?v=CgsWxRUY5Eo&t=0s)
Shah introduces the core issue: coding agents allow engineers to author code at a 10x faster pace, but this code isn't always optimized. Because AI agents lack specific knowledge of internal platforms and frameworks, they often introduce new, inefficient patterns, driving up compute costs and making manual performance engineering a major bottleneck.

### The Manual Performance Engineering Workflow [02:05](https://www.youtube.com/watch?v=CgsWxRUY5Eo&t=125s)
Shah outlines the traditional human workflow for performance engineering. It involves triggering a profiler on a single production instance, downloading raw data (like JSON call stacks), and visualizing it. Engineers spend significant time hunting for bottlenecks, searching codebases, and submitting fixes. This tedious, manual process is rarely done proactively—usually only during 2 a.m. emergencies.

### Hypothesis: LLMs Can Read Profiling Data [05:13](https://www.youtube.com/watch?v=CgsWxRUY5Eo&t=313s)
The foundational assumption for the experiment is that all profilers speak the same language. Whether the service is written in Java, Python, or Go, the output (call stacks, self CPU, inclusive CPU) is well-structured. Furthermore, LLMs are already trained on high-quality public code and inherently know common anti-patterns like O(N²) loops, loop invariants, and poor batching.

### The Experiment and First 'Aha' Moment [07:46](https://www.youtube.com/watch?v=CgsWxRUY5Eo&t=466s)
Netflix fed structured profiling data to an LLM. The agent successfully identified a quadratic algorithm (an immutable map copy inside a tensor merge method) purely by looking at the call stack data, without needing to see the codebase first. This proved that LLMs can recognize bad patterns directly from profiler output.

### End-to-End AI Agent Workflow [09:21](https://www.youtube.com/watch?v=CgsWxRUY5Eo&t=561s)
Once the AI identifies a problem in the profiling data, it can execute a multi-step workflow: perform a code search, clone the Git repo at the exact commit running in production, trace the method's call path, and generate a code review. In one real production example, the agent identified an O(N²) loop consuming 8.8% of CPU time and submitted a fix in under 5 minutes.

### Scaling Fixes Across Multiple Services [12:29](https://www.youtube.com/watch?v=CgsWxRUY5Eo&t=749s)
The AI agent can scale fixes beyond a single service. In one case, the agent identified a bad pattern (creating a counter object on every iteration of a hot path) and used cross-repo code searches to find the same anti-pattern in seven different services, projecting CPU savings between 0.5% and 4.6% across the fleet.

### Building Long-Term Memory: The Pattern Catalog [14:34](https://www.youtube.com/watch?v=CgsWxRUY5Eo&t=874s)
To build an agent as efficient as a human engineer, it needs long-term memory. Shah proposes a centralized, ever-growing catalog of patterns and anti-patterns stored as markdown files in a Git repo. This stateful catalog combined with a stateless LLM creates fleet-wide memory. The catalog can be bootstrapped from public sources (like Jeff Dean's C++ optimization notes or PyTorch's anti-pattern repo) and internal performance playbooks.

### Human-in-the-Loop and Canary Validation [20:46](https://www.youtube.com/watch?v=CgsWxRUY5Eo&t=1246s)
To manage noise and risk, Shah emphasizes keeping a human in the loop to approve code reviews. Before requesting human attention, the agent should run unit/integration tests. More importantly, the agent should use canary deployments—sending the same traffic to an old instance and a new instance for 10 minutes to compare CPU, latency, and error rates. The profiler gives the estimate, but the canary provides the ground truth.

### Shifting Left in the Development Cycle [24:24](https://www.youtube.com/watch?v=CgsWxRUY5Eo&t=1464s)
The reactive path (fixing production code) is a starting point, but the ultimate goal is to shift left. As the pattern catalog grows, a reviewer agent can leave inline comments during code reviews. Even better, the catalog can be hooked directly into coding agents during the code authoring phase, preventing inefficient code from being written in the first place.

### Foundations and Maturity Model [27:29](https://www.youtube.com/watch?v=CgsWxRUY5Eo&t=1649s)
Shah stresses that AI cannot fix broken foundations. Test coverage, business logic encoding, and canary automation must be solid before introducing AI. He outlines a maturity model: Level 1 (Current state: manual, no LLM), Level 2 (Orchestration: fixed workflows where the AI triggers profiles, runs canaries, and suggests fixes on a schedule), and Level 3 (Autonomy: the agent plans and reasons, requiring heavy investment in security and sandboxing). He advises starting at Level 1 and moving to Level 2 for maximum benefit.
