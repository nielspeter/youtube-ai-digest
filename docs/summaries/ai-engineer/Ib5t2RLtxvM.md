## TL;DR
Rustem Feyzkhanov explains how companies can turn production agent traces into repeatable offline simulation benchmarks, enabling reliable evaluation, release gating, and continuous improvement of AI agents. He outlines the anatomy of a benchmark task—environment, verifiers, and Oracle solutions—and argues that every organization shipping agents to production needs a private, domain-specific benchmark integrated into their agent ops lifecycle.

## Key Takeaways
- Every company deploying AI agents needs a private, domain-specific benchmark; public benchmarks are useful for orientation but insufficient for shipping production agents.
- Traces are valuable for finding production failures, but only offline simulations allow repeatable, apples-to-apples comparison of agent configurations.
- A benchmark must mimic production as closely as possible—real tools, APIs, databases, policies, and workflows—so the agent doesn't know it's in simulation.
- Beyond pass rate, simulations let you measure cost, latency, retries, and full-stack performance, not just model quality.
- Benchmarks serve a trifecta of purposes: agent evaluation, integration test/release gate, and training data for fine-tuning.
- The Harbor format (from the TerminalBench team) structures benchmark tasks as instruction files, Docker-based environments, Oracle solutions, verifiers, and metadata.
- Verifiers can be deterministic checks, LLM-as-a-judge, or human subject matter expert review for disputed cases.
- Benchmark development is a software engineering discipline requiring its own CI pipeline, Oracle validation, difficulty tagging, and approval workflows.
- The anti-pattern of stuffing every fix into the prompt should be avoided; simulations let you place fixes in the correct layer (hardness, skills, structured output, etc.).
- In production, two loops run continuously: benchmark expansion from observability traces and simulation experiments that serve as release gates.

## Detailed Breakdown

### Introduction and Core Thesis [00:01](https://www.youtube.com/watch?v=Ib5t2RLtxvM&t=1s)
Rustem Feyzkhanov introduces himself as leader of the AI platform team at Snorkel AI, a data-as-a-service company that produces benchmarks at scale, running millions of agent simulations per month. He frames his talk around three takeaways: every company needs a benchmark, it must closely mimic production, and it must be part of the agentic lifecycle as a living dataset populated from production traces.

### Why Traces Aren't Enough [02:06](https://www.youtube.com/watch?v=Ib5t2RLtxvM&t=126s)
Traces—showing input prompts, agent actions, and outputs—are useful for finding production failures but make it hard to test different agent variants reliably. A/B testing in production suffers from non-repeatability: database states, tool versions, and other variables constantly shift, so you never fully compare apples to apples. Offline simulation converts traces into repeatable experiments where you can compare agents on success rate, cost, latency, and retries in parallel.

### Public vs. Private Benchmarks [03:10](https://www.youtube.com/watch?v=Ib5t2RLtxvM&t=190s)
Public benchmarks like SweepBench (GitHub issue fixing), TerminalBench (terminal agents), and Co-Bench (computer use) are domain-specific and useful for building priors about model capabilities. However, they focus heavily on pass rate, which matters for model releases but not enough for production agents where cost, latency, and retries also matter. A private benchmark tailored to your company's use cases, tooling, and policies is what actually lets you ship. Public benchmarks orient you; private benchmarks let you ship.

### What a Benchmark Unlocks [04:43](https://www.youtube.com/watch?v=Ib5t2RLtxvM&t=283s)
Simulations let you test the full agent stack—not just which model performs better, but thinking levels, prompts, tools, and configurations—while keeping the environment and evaluators constant. Benchmarks serve three stages: first release (validate it works, select models, debug traces), release gating (catch regressions, iterate on difficulty), and optimization (tune for cost/latency or use traces for fine-tuning). Feyzkhanov mentions an example on Snorkel's website where simulation environments were used to fine-tune a small planning model to match a large one for specific tasks.

### Anatomy of a Benchmark Task [06:19](https://www.youtube.com/watch?v=Ib5t2RLtxvM&t=379s)
A benchmark task follows a straightforward sequence: the agent receives an input prompt, interacts with an environment (APIs, MCP tools, databases, files), produces output plus trace and artifacts, and then verifiers generate metrics. An Oracle solution runs the same sequence to confirm the task is solvable. Feyzkhanov references the Harbor format, which structures tasks as instruction files (what the agent sees), Dockerfile or Docker Compose environments, Oracle solutions and verifiers (hidden from the agent), and metadata.

### Building the Environment [08:25](https://www.youtube.com/watch?v=Ib5t2RLtxvM&t=505s)
The environment must be a "mini production" without the overhead of running full production for every experiment. It should include realistic databases, API services, tools, and files. Since you can't place a real user in simulation, you simulate the user with an LLM prompted to mimic human behavior. Patterns include using database snapshots, sidecar containers for APIs and tools, mocking API services, and supporting multi-step tasks with intermediate prompts and verifiers for long-horizon workflows.

### Verifiers [10:32](https://www.youtube.com/watch?v=Ib5t2RLtxvM&t=632s)
Unlike traditional output verification, agent simulation verifiers analyze the final environment state (database changes, API responses, user replies), the trace, and artifacts. Approaches include deterministic checks for clear-cut cases (final output, tool calls), LLM-as-a-judge or agent-as-a-judge for trace quality and planning assessment, and selective human subject matter expert review for cases with disagreement between agent behavior and verifier results.

### Benchmark CI and Quality Control [12:03](https://www.youtube.com/watch?v=Ib5t2RLtxvM&t=723s)
Benchmark tasks can fail in many ways: agents reward-hack the simulation, verifiers are too broad (always pass) or too strict (always fail), or results are unstable with high variation. Benchmark development is a software engineering discipline requiring a dedicated CI pipeline. Checks include pinning dependencies, validating base images, ensuring fixtures aren't missing, running Oracle solutions to confirm they pass, verifying that agents without Oracle fail, running multiple agent runs to confirm solvability and difficulty, tagging tasks by difficulty, and approving tasks for inclusion.

### Agent Improvement Workflow [14:10](https://www.youtube.com/watch?v=Ib5t2RLtxvM&t=850s)
The improvement process involves establishing a baseline on the benchmark, identifying failures, changing one variable, rerunning experiments (using tools like Arize to record them), and then rerunning the full suite before releasing. Feyzkhanov calls out the anti-pattern of pushing all fixes into the prompt with instructions like "never do this." With simulation control over the full stack, fixes should live in the right place: context overload addressed via hardness, missing procedures added as skills, and output requirements enforced via structured output.

### Production Loops and Conclusion [15:12](https://www.youtube.com/watch?v=Ib5t2RLtxvM&t=912s)
Once in production, two loops operate continuously: benchmark expansion (capturing observability traces and failures to extend the benchmark) and simulation experiments (running new agent configs on the extended benchmark as a release gate). Feyzkhanov stresses that observability and experimentation must be connected as two sides of the same coin. He closes by reiterating his three takeaways: every company needs a benchmark, traces find edge cases but simulations test what would happen, and benchmarks must be part of agent ops.

### Q&A [16:48](https://www.youtube.com/watch?v=Ib5t2RLtxvM&t=1008s)
On structuring benchmarks, Feyzkhanov recommends a traditional 80/20 train-validation split, ensuring a standalone dataset the agent hasn't seen. For coverage, benchmarks should include both "bread and butter" happy-path use cases and edge cases (tool failures, database problems), treating it like integration testing. On building benchmarks, much can be automated with agents, but the key human contribution is building the environment once and providing production-mimicking context. For verifiers, subject matter experts should focus specifically on cases where there's disagreement between agent behavior and verifier results, tuning the reviewing agent accordingly.
