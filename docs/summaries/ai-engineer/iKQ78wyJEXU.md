# We Vetted 2000 AI Skills Before They Reached Developers — Lucas Palma, Nubank

[![We Vetted 2000 AI Skills Before They Reached Developers — Lucas Palma, Nubank](https://i.ytimg.com/vi/iKQ78wyJEXU/hqdefault.jpg)](https://www.youtube.com/watch?v=iKQ78wyJEXU)

## TL;DR
Lucas Palma (LP), Product Security Manager at Nubank, explains how the company built a security review system called **Skill Vector** to vet over 2,000 AI skills before they reached developers via an internal marketplace. By combining deterministic scanners with LLM-based contextual review, Nubank identified and remediated over 1,500 risks—treating AI skills as supply-chain dependencies and protecting the entire developer workflow, not just generated code.

## Key Takeaways
- **AI skills behave like supply-chain dependencies**: Although they look like configuration, they carry the same risk profile as third-party libraries and packages.
- **The AI supply chain has expanded**: It now includes skills, plugins, MCP servers, agent rules, and hooks—not just traditional package containers and models.
- **AI skills can be dangerous in specific ways**: hardcoded tokens leaking into logs, destructive shell commands, excessive permissions, and unintentional data exposure.
- **Marketplace as a security boundary**: Nubank created an internal marketplace where skills are canonically shared, with a CI gate (Skill Vector) inserted before any skill is published.
- **Hybrid scanning approach**: Deterministic checks (regex-based) handle straightforward patterns; LLM review provides contextual behavioral analysis. Both are needed because LLMs alone are inconsistent.
- **PR-integrated feedback**: Findings are reported directly on the pull request, improving developer usability and ensuring remediation happens before marketplace distribution.
- **SARIF output enables vulnerability management**: Scan results are exported in SARIF format so they can be consumed by existing security tools and fed into Nubank's vulnerability management program.
- **Human-in-the-loop is not guaranteed**: An instruction to "ask for confirmation" can be satisfied by the AI confirming with itself—proper approval gates and hooks are required.
- **The framework is extensible**: The same model applies to plugins, MCP servers, rules, and hooks, with different risk profiles and gates.
- **Third-party skills must go through the same pipeline**: Downloaded skills must be uploaded to the marketplace so they receive the same scanning before use.

### Introduction and Speaker Background [00:01](https://www.youtube.com/watch?v=iKQ78wyJEXU&t=1s)
Lucas Palma (LP) introduces himself as the Product Security Manager at Nubank, where his team focuses on making code safe and supporting engineers, product managers, and others in building safer products. ### Why AI Skills Are a Supply-Chain Risk [01:04](https://www.youtube.com/watch?v=iKQ78wyJEXU&t=64s)
LP frames the core problem: AI skills are now part of the developer workflow, and while they look like configuration, they behave like supply-chain dependencies. The traditional supply chain included package containers and models, but the AI era adds skills, plugins, MCP servers, agent rules, and more. The key lesson is that organizations must protect the entire workflow, not just the code being generated.

### What Is an AI Skill and Why It Matters [02:37](https://www.youtube.com/watch?v=iKQ78wyJEXU&t=157s)
An AI skill bundles instructions and context into a model or agent to provide better guidance for code generation. However, because skills can be created by one person and shared with others, the original author effectively guides the code generated by downstream users. In a regulated financial environment, this creates tension between developers wanting faster, less repetitive coding and the need for auditability, credential safety, and security by default.

### Examples of Dangerous AI Skills [04:44](https://www.youtube.com/watch?v=iKQ78wyJEXU&t=284s)
LP gives concrete examples of how skills can be dangerous:
- A skill may instruct the AI to retrieve and hardcode a token, which then leaks into logs.
- A skill may instruct the AI to use shell commands that, when executed on another developer's shell, can modify files or cause other damage.
- A skill may be configured with excessive permissions beyond what is needed.
- Even a typo in a skill configuration can lead to dangerous behavior depending on the user.

### Marketplace as the Security Boundary [05:47](https://www.youtube.com/watch?v=iKQ78wyJEXU&t=347s)
Nubank's solution starts with an internal marketplace where engineers discover and share skills canonically. When someone creates or modifies a skill, they open a pull request. Before the skill reaches the marketplace, a CI step runs **Skill Vector**, a tool that assesses whether the skill is safe, classifies risks, and requests remediation as needed.

### How Skill Vector Works [06:51](https://www.youtube.com/watch?v=iKQ78wyJEXU&t=411s)
Skill Vector operates in multiple stages:
1. **Local scan**: Engineers can run Skill Vector locally and iterate until the skill is considered safe.
2. **Post-upload scan**: After upload, Skill Vector runs again to ensure the latest version is scanned.
3. **Deterministic checks**: Regex-based scanners catch easy, non-contextual risks.
4. **LLM review**: For risks requiring contextual understanding, an LLM reviews the skill's behavior. LP emphasizes the hybrid approach because LLMs alone are inconsistent depending on temperature settings.
5. **PR feedback**: All findings are reported as comments on the pull request, so the engineer sees exactly what needs to change.
6. **SARIF export**: Results are exported in SARIF format for consumption by security tools and the vulnerability management program.
7. **Decision**: Based on severity and policy, the skill is allowed, requires remediation, or is blocked before marketplace distribution.

### What Skill Vector Scans For [09:29](https://www.youtube.com/watch?v=iKQ78wyJEXU&t=569s)
The non-exhaustive list of checks includes:
- Unsafe instructions
- Behavioral drift in the agent
- Destructive shell commands
- Unauthorized file modifications
- Credential request patterns
- Unintentional data exposure
- Over-broad or risky permissions
- Risky MCP usage

### Results: 2,000+ Skills Scanned [10:00](https://www.youtube.com/watch?v=iKQ78wyJEXU&t=600s)
Skill Vector has scanned over 2,000 skills (more by the time of the talk). Across those skills, more than 1,500 individual risks were identified. Approximately 1,000 were remediated immediately, and a smaller number of high-risk skills were blocked before reaching the marketplace. Nubank also ran a historical scan on skills created before Skill Vector existed, identifying additional risks and feeding them into the vulnerability management program.

### Lessons Learned: What Worked and What Needed Improvement [11:03](https://www.youtube.com/watch?v=iKQ78wyJEXU&t=663s)
**What worked well:**
- Combining deterministic scanners with LLM review for behavioral checking.
- Outputting results in SARIF and adding PR comments for actionable feedback.

**What needed improvement:**
- Some shell comments were treated equally in risk severity, but actual risk varies by comment.
- Weak signals without enough context were more noisy than helpful.
- The "ask for confirmation" prompt-level pattern was problematic (see next section).
- Some warnings seemed harmless for local use but were impactful in production.
- Findings without clear remediation guidance were troublesome for engineers.
- Other marketplaces could appear outside the canonical one, requiring proactive scanning coverage.

### The Human-in-the-Loop Illusion [12:37](https://www.youtube.com/watch?v=iKQ78wyJEXU&t=757s)
LP highlights a subtle but critical issue: a skill may instruct the AI to "ask for confirmation," but the AI may ask confirmation of itself and then proceed. From the developer's perspective, a human was in the loop, but from the AI's perspective, confirmation already occurred. Skill Vector scans for this pattern and checks whether proper approval gates, hooks, and tool-level enforcement are in place to ensure a genuine human-in-the-loop.

### Reusable Lessons and Broader Applicability [13:40](https://www.youtube.com/watch?v=iKQ78wyJEXU&t=820s)
LP emphasizes that the lessons from securing skills apply broadly:
- Treat AI components (skills, plugins, MCP servers, rules, hooks) as supply chain.
- Review everything before it reaches the marketplace.
- Let developers run checks locally and enforce the same checks in CI.
- Combine deterministic and LLM-based checks.
- Enforce dangerous-action prompting and tool-level audit logs and trusted gateways.
- Maintain a trusted AI marketplace that covers both internally created and third-party skills/plugins.

### Next Steps and Closing [14:46](https://www.youtube.com/watch?v=iKQ78wyJEXU&t=886s)
Next steps include extending the same scanning model to MCP servers (MCP Vector), rules checks, and hooks—with different risk profiles and gates depending on policy and marketplace. LP stresses the importance of a trusted AI marketplace where even third-party downloaded skills must be uploaded and scanned before use, ensuring all developers can use them safely.
