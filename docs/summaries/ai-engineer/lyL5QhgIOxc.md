# Serving 2 Million Models Without Melting: Scaling the Hugging Face Hub — Arek Borucki, Hugging Face

[![Serving 2 Million Models Without Melting: Scaling the Hugging Face Hub — Arek Borucki, Hugging Face](https://i.ytimg.com/vi/lyL5QhgIOxc/hqdefault.jpg)](https://www.youtube.com/watch?v=lyL5QhgIOxc)

## TL;DR
Arek Borucki, ML platform and database engineer at Hugging Face, explains how the Hub scaled from 20,000 to 3 million public models by separating metadata (MongoDB Atlas) from binary artifacts (S3), optimizing search with pre-computed tokens and Apache Lucene-backed Atlas Search, distributing reads across a 7-node replica set, and autoscaling Kubernetes pods with plans to adopt KEDA for event-driven scaling. The overarching theme is keeping the user experience simple even as the underlying infrastructure grows increasingly complex.

## Key Takeaways
- Hugging Face now serves 14 million users, 3 million public models, 1 million datasets, and 50,000 organizations — with 30%+ of Fortune 500 companies using the platform.
- MongoDB Atlas stores all metadata (users, repos, models, datasets, billing, access control) but not the actual model artifacts, which live in cloud object storage like AWS S3, allowing each layer to scale independently.
- Search was optimized by pre-tokenizing model names at insert time into a denormalized read-only collection, then switching from MongoDB's `regex` operator to Atlas Search (powered by Apache Lucene) for fast autocomplete queries.
- The MongoDB cluster uses 7 nodes: a primary for all writes, multiple secondaries for distributed reads, and a hidden analytic node isolated from production traffic for heavy reporting and ad-hoc queries.
- P99 latency is treated as more important than P50, because with 14 million users even 1% experiencing slow search means 140,000 affected people.
- The Hub runs on Kubernetes with a two-layer autoscaling approach: Horizontal Pod Autoscaler (10–500 pods) for deployment-level scaling and Cast AI for cluster node-level scaling when capacity runs out.
- Hugging Face plans to migrate from HPA (CPU/memory-based) to KEDA (Kubernetes Event-Driven Autoscaling), which scales on real application metrics like requests per second or event loop utilization.
- The next database scaling step is sharding — splitting data horizontally across multiple replica sets, each holding only a portion of the dataset, to scale CPU, memory, storage, reads, and writes.
- Major model releases like Llama and DeepSeek generate thousands of new models, creating traffic spikes the infrastructure must absorb automatically.
- The ultimate goal is a seamless user experience: users never have to think about the infrastructure complexity behind pushing, searching, or downloading models.

## Detailed Breakdown

### Introduction and Scale of Hugging Face [00:01](https://www.youtube.com/watch?v=lyL5QhgIOxc&t=1s)
Arek Borucki introduces himself as a machine learning platform and database engineer at Hugging Face. He notes that nearly everyone in the audience already uses Hugging Face, yet there is still room for growth. The Hub has grown from 20,000 models a few years ago to 3 million today — a roughly 150x increase. It now serves 14 million users, hosts 1 million datasets and 50,000 organizations, and is used by more than 30% of Fortune 500 companies. Major releases like Llama and DeepSeek each generate thousands of new derivative models, and datasets have grown from 10K in 2022 to 1 million today, all of which must be stored, indexed, and searchable.

### The Search Problem at Scale [04:20](https://www.youtube.com/watch?v=lyL5QhgIOxc&t=260s)
Borucki explains that at 20,000 models, any query is fast even without an index. At 3 million, the same approach breaks. Users expect instant results, and with 14 million users, even 1% experiencing slow search means 140,000 people are affected. This is why Hugging Face prioritizes P99 latency over P50. The investments they made include pre-computed tokens, denormalized read-optimized collections in MongoDB, full-text search via Apache Lucene, Kubernetes autoscaling, and upcoming database sharding.

### High-Level Architecture [05:51](https://www.youtube.com/watch?v=lyL5QhgIOxc&t=351s)
Requests flow from the front end to the Hub API, which runs on Kubernetes with Horizontal Pod Autoscaler. The Hub's source of truth for metadata is MongoDB Atlas. A key architectural point: MongoDB does not store the model artifacts themselves — it stores everything *about* the models (metadata, users, repositories, datasets, billing, access control, etc.). The actual artifacts (tokenizer files, card assets, configuration files) are stored in cloud object storage such as AWS S3. This separation of concerns allows metadata, binary storage, and compute to each scale and be optimized independently.

### Search Implementation in Detail [07:58](https://www.youtube.com/watch?v=lyL5QhgIOxc&t=478s)
When a user searches for "llama," the request goes to a denormalized, read-optimized collection in MongoDB — separate from the main repository collection. Model names are tokenized at insert time, not query time. For example, `meta-llama/llama-3.1-8b` is split into tokens like `meta`, `llama`, `3.1`, `8b` and stored in a `searchTokens` array. Previously, Hugging Face used MongoDB's `find` method with a `regex` operator on this array, sorted by a trending score (downloads and likes from the last 7 days, recalculated every 5 minutes). This worked when the dataset was small, but `regex` does not scale well, causing latency problems as data grew.

### Migration to Atlas Search [11:11](https://www.youtube.com/watch?v=lyL5QhgIOxc&t=671s)
To solve the latency issue, Hugging Face switched to MongoDB Atlas Search, which uses Apache Lucene under the hood via a separate `mongot` process. For users, this is transparent — they use the unified MongoDB query API with an aggregation pipeline and the `$search` operator, specifying the index name (e.g., `model_search_autocomplete`). This solution proved much more efficient and resolved the search bar latency issues. Borucki shows an example where the top result for "llama" has a trending score of 33 and the second has 14.

### MongoDB Cluster Topology and Read Distribution [13:17](https://www.youtube.com/watch?v=lyL5QhgIOxc&t=797s)
The MongoDB cluster consists of 7 nodes. All inserts, updates, and deletions go to a single primary. Reads are distributed across multiple secondary nodes to prevent any single node from becoming a read bottleneck. There is also one hidden analytic node that replicates from the primary but is invisible to the MongoDB driver — no production queries are routed to it. Hugging Face connects directly to this node for heavy reporting and analytical queries. All secondaries continuously tail the primary's oplog to stay in sync.

### What Runs on Secondaries [14:50](https://www.youtube.com/watch?v=lyL5QhgIOxc&t=890s)
Four categories of workloads are pushed off the primary: (1) queries that do not require the latest data go to secondaries, with strong-consistency queries staying on primary; (2) complex aggregation pipelines that scan, sort, group, or transform large amounts of data; (3) change streams for real-time reactions to data changes (cache validation, syncing to data stores like AWS Redshift, event-driven workloads); and (4) all ad-hoc, reporting, and experimental queries go to the hidden replica set member. The guiding principle: the primary should only do what only the primary can do.

### Database Sharding as the Next Step [16:30](https://www.youtube.com/watch?v=lyL5QhgIOxc&t=990s)
With continued growth, a single MongoDB replica set will not suffice. The next step is sharding — horizontal scaling where data is cut into pieces, each placed on a separate shard with its own primary and secondaries. Unlike a replica set (full dataset on every node), a sharded cluster holds only part of the data per shard. The MongoDB balancer distributes data across shards, and a shard key must be selected (though Borucki notes that topic is beyond this talk). Sharding scales CPU, memory, storage, reads, and writes simultaneously.

### Kubernetes Autoscaling — Two Layers [18:02](https://www.youtube.com/watch?v=lyL5QhgIOxc&t=1082s)
The Hub deployment runs on Kubernetes with Horizontal Pod Autoscaler (HPA), scaling from 10 to 500 pods based on CPU and memory thresholds. If HPA wants to add pods but no free nodes are available, Cast AI adds new nodes at the infrastructure level so the scheduler can place pending pods. This two-layer approach (deployment-level and infrastructure-level) keeps the Hub healthy without manual intervention or overprovisioning, making it cost-effective.

### Migration to KEDA [20:07](https://www.youtube.com/watch?v=lyL5QhgIOxc&t=1207s)
Hugging Face plans to migrate from HPA to KEDA (Kubernetes Event-Driven Autoscaling). HPA scales only on CPU and memory, while KEDA scales on real application metrics like requests per second or event loop utilization. For example, a pod might have low CPU but high request queue depth — KEDA can detect this, but HPA cannot. Borucki closes by emphasizing that the best part of the architecture is that users never have to think about it: pushing a model, searching, or downloading just works.
