## TL;DR
Divakar Kumar from FlyersSoft presents a practical architecture for integrating AI agents into existing event-sourced systems, using real-time fraud detection as the primary use case. The key insight is that AI agents add the most value not in chatbots or coding assistants, but in resolving "gray zone" business decisions where traditional rule-based and ML-based engines lack sufficient cross-domain context to make confident verdicts.

## Key Takeaways
- AI agents deliver real business value when applied to uncertain "gray zone" decisions that existing rule-based and ML systems cannot confidently resolve, rather than replacing those systems entirely.
- A tiered approach works best: Tier 1 handles the majority of transactions via traditional rules/ML, while Tier 2 uses agentic AI only for ambiguous cases.
- Bounded contexts in DDD-based architectures naturally limit data sharing, making it difficult to provide AI agents with comprehensive context—but this can be solved with a projection/semantic layer.
- Event sourcing with a change feed (CDC) mechanism enables propagating domain events from an event store into multiple read models optimized for different query needs.
- A fan-out pattern with multiple specialized agents (risk analyzer, behavior analyzer) feeding into a third verdict agent produces more reliable conclusions than single-agent approaches.
- Short-term (in-memory) memory is preferred over long-term memory when sub-500ms SLAs must be met for transaction processing.
- The agentic loop must have clear termination criteria to avoid infinite loops, with metrics varying by use case.
- Saga orchestration integrates the agentic layer seamlessly, with verdicts emitted as events back into the message broker to continue the business flow.
- Tools act as the bridge between AI agents and the projection/semantic layer, giving agents access to denormalized data from all bounded contexts.
- The architecture is not limited to event-sourced systems—it works with any event-driven or relational database setup, provided a semantic layer is built for agent context.

## Detailed Breakdown

### Introduction and Problem Space [00:01](https://www.youtube.com/watch?v=o6U_2vd967Y&t=1s)
Divakar opens by framing the session around integrating AI agents into existing business systems—whether event-sourced, event-driven, or any architecture a business has invested in. He emphasizes that AI agents are not just for chatbots or coding assistants, but deliver real value when applied to business workflows. The chosen problem space is real-time fraud detection.

### Personal Experience with Fraud Detection [01:33](https://www.youtube.com/watch?v=o6U_2vd967Y&t=93s)
He shares a personal anecdote about attempting to purchase a $3,500 laptop. After two declined transactions, he received a call from customer service to verify the transaction. When he asked why it was blocked, the customer service representative didn't know—the decision was made somewhere in the system by a rule-based or ML-based engine, possibly based on transaction history or an average threshold. This highlights the opacity and lack of context in traditional fraud detection systems.

### The Case for AI Agents in Uncertain Areas [02:36](https://www.youtube.com/watch?v=o6U_2vd967Y&t=156s)
Divakar acknowledges the apparent contradiction of introducing non-deterministic AI agents into already uncertain situations. However, he argues that the real issue is that rule-based and ML-based engines lack sufficient real-time context and data from different domain contexts. The goal is to build an architecture that gives AI agents access to this cross-domain data so they can produce a well-informed verdict.

### Evolution from Rule-Based to ML to Agentic AI [03:38](https://www.youtube.com/watch?v=o6U_2vd967Y&t=218s)
The team started with a rule-based engine five years prior, which worked but suffered from maintainability issues as fraudsters constantly found new intrusion methods requiring static rule updates. They then partnered with a third-party provider to develop an ML model trained on transaction history and features, producing a risk score. However, both approaches struggle with transactions in the "gray zone"—cases that fall between clear approve and clear block thresholds, where the system cannot confidently determine if a transaction is fraudulent or legitimate.

### Tiered System Architecture [05:14](https://www.youtube.com/watch?v=o6U_2vd967Y&t=314s)
Rather than replacing existing systems, the team built a two-tier architecture. Tier 1 retains the rule-based and traditional ML engines, handling the majority of transactions well. Tier 2 introduces agentic AI processing specifically for gray-zone cases. This approach preserves existing investments while augmenting them with AI capabilities.

### Bounded Contexts and Domain Complexity [05:45](https://www.youtube.com/watch?v=o6U_2vd967Y&t=345s)
Divakar describes their domain's bounded contexts following DDD principles. The transaction context holds merchant details, amounts, and transaction data but knows nothing about customers, payments, or devices. The accounts context manages KYC compliance and customer information. The device context stores device fingerprints, browser fingerprints, and OS details useful for fraud detection. The payment context handles chargebacks and payment-related data. These contexts don't share data directly, requiring asynchronous communication patterns typical of microservices.

### Orchestrator Layer and Agentic AI Integration [07:47](https://www.youtube.com/watch?v=o6U_2vd967Y&t=467s)
To solve the cross-context data sharing problem, the team introduced an orchestrator layer—similar to saga orchestration—where all communication flows through a central layer that routes events to interested services. They then embedded agentic AI within this orchestrator. Asynchronous communication between contexts happens via a message broker.

### Event Sourcing and Read Models [08:17](https://www.youtube.com/watch?v=o6U_2vd967Y&t=497s)
Zooming into the transaction context, Divakar explains their event-sourcing methodology. Domain events like "transaction created" mark the start of a transaction, while integration events like "transaction rejected," "payment approved," and "payment rejected" arrive from other contexts. All events are stored as immutable business facts in Cosmos DB (their event store) using an append-only model rather than state mutation. A CDC (change feed) mechanism notifies on changes, propagating them into multiple read models: timelines, customer information, and fraud indicators/risk view. Since other teams don't follow event sourcing, events are also emitted to a message broker, processed by a worker process, and stored in a materialized view (semantic layer).

### Building the Semantic/Materialized View Layer [10:53](https://www.youtube.com/watch?v=o6U_2vd967Y&t=653s)
The high-level flow involves using either CDC or a message broker to propagate events from all bounded contexts into a projection layer. An intermediate worker process massages and processes events before storing them in the materialized view. This semantic layer aggregates denormalized data from all contexts, providing the comprehensive context that AI agents need.

### Anatomy of AI Agents [11:23](https://www.youtube.com/watch?v=o6U_2vd967Y&t=683s)
Divakar breaks down agents into three components: language models (which can be SLMs or open-source models, not necessarily LLMs), tools (for interacting with external APIs or application-layer methods), and memory. For this use case, they use short-term in-memory storage because long-term memory would violate their sub-500ms SLA for transaction processing. The agent's reasoning capability decomposes tasks into chunks, each processed with tools, looping until the end goal is reached or a termination metric is hit—carefully avoiding infinite loops.

### Saga Orchestration with Fan-Out Agent Pattern [13:28](https://www.youtube.com/watch?v=o6U_2vd967Y&t=808s)
Events from the transaction aggregate are emitted as integration events to the message broker, then handled by the orchestration layer. The orchestration layer is divided into Tier 1 (rule-based/ML) and Tier 2 (agentic AI). Tier 2 uses a fan-out pattern, dispatching events to two specialized agents: a risk analyzer agent and a behavior analyzer agent. Their responses feed into a verdict layer. Initially using simple metrics for verdicts led to false positives, so they introduced a third agent that analyzes both agents' responses and produces a final conclusion, emitted as an event back to the message broker to continue the saga flow into the payment context.

### Agent Tools and Context Gathering [15:45](https://www.youtube.com/watch?v=o6U_2vd967Y&t=945s)
The risk analysis agent has tools for retrieving fraud histories from the semantic layer, accessing device trust information, and applying migrated business rules. The behavior analysis agent examines transaction patterns using two plugins. The projection layer provides denormalized data: transaction context contributes counts, averages, and recent transactions; device context provides device trust scores, location histories, and IP addresses; account context provides KYC status and account age; payment context provides recent payment data. Tools access this projection layer, which agents use to reach conclusions.

### POC Demonstration [19:11](https://www.youtube.com/watch?v=o6U_2vd967Y&t=1151s)
Divakar demonstrates a POC using synthetic data across the transaction, accounts, and device contexts. Events propagate through different layers via a CDC mechanism into the semantic layer used by AI agents. Multiple simulation events populate through the system, showing Tier 1 ML processing followed by Tier 2 agentic processing, where two agents produce separate conclusions and a third agent makes the final decision—emitted as an event back to the message broker to continue the saga flow.
