# MCP Tasks (async): Why Aren't Any Agents Supporting Them? — Cornelia Davis, Temporal

## TL;DR
Cornelia Davis explores why MCP clients haven't adopted the MCP Tasks specification for asynchronous, long-running tools: the V1 spec is marked experimental, stateful, and notoriously complex to implement. She demos a purchase-order workflow built on Temporal, walks through the V1 protocol's pain points, and highlights how the upcoming V2 spec moves to a stateless core with cleaner signaling—though significant durability and scaling challenges remain.

## Key Takeaways
- MCP Tasks enable long-running, asynchronous MCP tool invocations that return a handle rather than an immediate response.
- The November 2024 V1 spec was marked experimental, and no major MCP clients have implemented it yet—largely because it's complex and stateful.
- Tasks must be durable: they must survive network blips, process crashes, human delays, and server/client downtime.
- V1's `task/list` endpoint is unfiltered and doesn't scale—retrieving tasks from a server with millions in flight is impractical.
- V1's `task/result` uses a long-running, session-based "elicitation" protocol for human-in-the-loop input, which is fragile and hard to implement.
- The V2 spec (expected July) moves MCP to a stateless core with a structured extension model; tasks become an extension.
- V2 removes `task/list`, replaces session-based elicitation with a simpler client-to-server "update" signal, and keeps the task lifecycle model intact.
- Even in V2, clients should persist task IDs—without doing so, there's no way to recover a task handle after a disconnection.
- Davis implemented her own MCP client ("task tracker workflow") using Temporal and FastMCP to demonstrate durable task tracking and signaling.
- Future work includes a notifications protocol to avoid polling at scale and a FastMCP integration to simplify client-side adoption.

A simple sequence diagram shows the client invoking a tool and receiving a handle instead of a result. But long-running tasks face infrastructure blips—network drops, humans on vacation, process crashes. The spec mandates that tasks be durable: once launched, they cannot disappear and must survive disconnections and downtime on both client and server sides.

### Live Demo: Submitting a Purchase Order [07:17](https://www.youtube.com/watch?v=s4r6nk5WsZw&t=437s)

### Tasks V1: Tool Semantics and Lifecycle [11:24](https://www.youtube.com/watch?v=s4r6nk5WsZw&t=684s)
The V1 spec defines a task lifecycle: working → input required → working → completed/canceled/failed. Tool semantics include `tools/call` (with async metadata), `task/get`, `task/cancel`, `task/list`, and `task/result`. The top four are request-response; `task/result` keeps a connection open for elicitation.

### V1 Challenges: task/list and task/result [12:58](https://www.youtube.com/watch?v=s4r6nk5WsZw&t=778s)
Two major problems: `task/list` is a stateful, unfiltered endpoint—if a server has a million tasks, the client must scan all of them to find the relevant one. `task/result` uses a long-running session where the server elicits input from the client, creating a fragile protocol that's difficult to implement and recover from if the connection drops.

### V2: Stateless Core and Structured Extensions [16:01](https://www.youtube.com/watch?v=s4r6nk5WsZw&t=961s)
In May, Angie Jones (Agoric AI Foundation) announced MCP is going stateless—music to the ears of anyone who's worked in large-scale distributed systems. V2 introduces a structured core-plus-extensions model; tasks become an extension. `task/list` is removed. Session-based elicitation is replaced by a client-to-server "update" signal (analogous to Temporal's signal mechanism). The task lifecycle model is preserved.

### V2 Client Responsibilities and Scaling Concerns [19:08](https://www.youtube.com/watch?v=s4r6nk5WsZw&t=1148s)
With `task/list` gone, clients must persist task IDs themselves—the spec says they "should," though Davis notes it arguably should be a "must," since there's no recovery path otherwise. She also emphasizes the need to support multiple concurrent tasks across many agents.

### Second Demo: V1 Protocol Complexity and Task Tracker [20:10](https://www.youtube.com/watch?v=s4r6nk5WsZw&t=1210s)
Davis submits multiple POs and shows the V1 client-side protocol handler implemented as a Temporal workflow ("task tracker"). She highlights that the V1 reference implementation processed `input required` events in FIFO order, meaning you could only respond to the first pending task even with many in flight. Her implementation works around this limitation.

### Summary, Future Work, and FastMCP Integration [21:42](https://www.youtube.com/watch?v=s4r6nk5WsZw&t=1302s)
Davis contrasts the ugly V1 client-server protocol with the much cleaner V2 version. She shares a summary diagram of everything needed to implement tasks and points to a GitHub repo with all code. Two ongoing efforts: (1) a notifications protocol to avoid million-client polling at scale, and (2) implementing the client-side task support directly in FastMCP to simplify adoption.
