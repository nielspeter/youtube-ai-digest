## TL;DR
Sai Krishna Rallabandi argues that while building single-user agentic systems is largely solved, the next frontier is deploying agents in group settings (like group chats and wearable glasses) that are always on. He draws on eight months of production experience with an agent named Judith to outline three key engineering challenges unique to group-deployed agents: a boundary-level security layer ("Jatayu"), real-time evolving memory management, and context-aware privacy routing.

## Key Takeaways
- Today's agents are typically built for a "customer of size one," but the next generation will serve groups and run continuously on wearable hardware like glasses.
- Group settings introduce unique challenges around security, memory curation, and privacy that do not exist in single-user systems.
- Agentic systems cannot be secured like standard LLMs because their attack surface is vastly larger; guarding inputs is impractical, so security must be applied at the action boundary.
- Static security scans are insufficient because two individually benign skills can become malignant when combined at runtime (e.g., an OCR skill secretly passing PII to a reporting skill).
- A naive deterministic security approach (regex/traditional NLP) can catch some threats, but a LoRA fine-tuned Small Language Model (SLM) is needed to catch obfuscated attacks, like text interspersed with dots.
- In group chats, memory must be treated as the evolving identity of the agent; engineers must store atomic facts, not just compacted conversation history.
- Effective memory management requires continuously adapting relevance scorers to determine what to keep and what to forget, saving tokens and reducing latency.
- A shared assistant represents a new social contract where the same information can be public or private depending entirely on the context of the "room" it is deployed in.
- Privacy can be baked into the system by using a shared memory layer with different LoRA adapters for each user, rather than relying on code-based permissions.
- Agents in group settings tend to be over-communicative; models need to be trained to understand their role and determine when they should and should not speak.

## Detailed Breakdown

### Introduction and the Next Frontier for Agents [00:01](https://www.youtube.com/watch?v=s67bE2Ur3bY&t=1s)
Rallabandi opens by declaring that the AI community has successfully figured out how to build agentic systems—combinations of models, orchestration, and tools. However, he notes that almost every agent built today caters to a "customer of size one." He projects that the next era of agents will serve groups, operate on wearable hardware like glasses, and remain on all day. This shift from single-user to group settings poses uniquely different engineering challenges.

### Real-World Examples from the Judith Agent [03:06](https://www.youtube.com/watch?v=s67bE2Ur3bY&t=186s)
To illustrate group-agent dynamics, Rallabandi shares examples from "Judith," an agent he has deployed for eight months among friends and family. Examples include the agent DM'ing him privately with directions rather than posting them in a group chat, syncing family calendars, and speaking directly into his glasses (rather than over car media) to preserve privacy. He also highlights Judith's ability to curate evolving group conversations over time and assist his three-year-old daughter in learning, while keeping parents posted on her progress.

### The Security Layer: "Jatayu" and Action-Surface Defense [05:43](https://www.youtube.com/watch?v=s67bE2Ur3bY&t=343s)
Rallabandi introduces "Jatayu" (a mythological character) as the name for his security layer. He argues that agentic systems cannot be secured like standard LLMs because agents interact with the world, creating a vast attack surface across web pages, group messages, emails, and GitHub issues. Instead of trying to guard or filter everything the agent reads at the input level, he advocates for a deterministic, fast defense mechanism placed at the "action surface"—the moment the agent attempts to take an action, like reading bash variables or exporting data.

### Runtime Skill Audits and SLM Fine-Tuning [07:47](https://www.youtube.com/watch?v=s67bE2Ur3bY&t=467s)
Referencing recent research on colliding skills, Rallabandi explains that static scans of code are insufficient because two benign skills can become malignant at runtime. For example, an OCR skill might extract data, and a reporting skill might send that data—along with private user information—to a third party. To combat this, his team built a LoRA fine-tuned Small Language Model (SLM) that separates the data channel from the instruction channel. This learned model outperforms naive regex approaches, especially against obfuscated attacks like text interspersed with dots (e.g., "L.Ii.K.").

### Memory Curation in Group Settings [12:03](https://www.youtube.com/watch?v=s67bE2Ur3bY&t=723s)
In group chats, memory is not just a storage mechanism; it is the evolving identity of the agent. Rallabandi argues against naively storing everything and compacting it later. Instead, engineers should extract "atomic bits" of high-value information. He emphasizes the need to design auto-evaluators to ensure the right facts are extracted, hierarchically related, and temporally relevant. He also mentions the importance of building an injection engine that is aware of KV caching to avoid breaking the model during serving.

### Forgetting and Continuous Relevance Scoring [15:06](https://www.youtube.com/watch?v=s67bE2Ur3bY&t=906s)
To prevent memory from becoming bloated and increasing latency, Rallabandi discusses training a simple ML model or SLM to act as a continuous relevance scorer. Inspired by the paper "Learning What Not to Forget," he explains that in a group setting, context constantly evolves. A continuously adapting relevance scorer allows for knowledge-based compaction, saving tokens by intelligently deciding what information to forget over time.

### Privacy as a Social Contract and LoRA Adapters [16:39](https://www.youtube.com/watch?v=s67bE2Ur3bY&t=999s)
Rallabandi frames a shared assistant as a new social contract, noting that the same data (like a grocery list vs. health information) can be benign or highly private depending on the "room" in which it is presented. He suggests a neat trick inspired by the human brain: use a common shared memory layer but train different LoRA adapters for each user. This bakes permissions into the machine learning model itself, rather than relying on code. Finally, he notes that agents in groups tend to be over-articulative, and suggests training a classifier to determine the agent's role and when it is allowed to speak.
