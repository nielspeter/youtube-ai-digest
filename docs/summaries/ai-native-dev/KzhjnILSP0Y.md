## TL;DR
Tammuz Dubnov, founder and CTO of Autonomy AI, argues that becoming "AI native" means collapsing the handover gap between decision-makers (PMs, designers) and code execution by giving those who care about a feature the tools to build it. He warns that simply throwing more LLM budget at the same developers or handing tools like Claude Code to non-technical staff burns money without speeding up feature delivery. The key to measuring success, he says, is tracking PR counts, merge rates, and "zero-dev-touch" merges from non-technical contributors.

## Key Takeaways
- **AI native means collapsing handoffs**: The real bottleneck isn't code-writing speed; it's the multi-week handover between PM, design, and engineering. AI lets the person who cares and has authority also do the work.
- **Everybody gets an upgrade**: PMs tune features directly, engineers focus on architecture and refactoring, and senior engineers tackle harder problems—each role concentrates on what it actually cares about.
- **More tokens ≠ more velocity**: Uber 6x'd its AI budget and ran out in four months with leaders unable to link spend to faster shipping. Microsoft rolled back broad Claude Code access for similar reasons.
- **Only ~18% of AI spend ships**: An analysis of 2,400 companies found that just $18 of every $100 spent on AI goes to meaningful shipped code; the rest is rework, AI-generated bugs, and looping agents.
- **Shopify is a positive model**: Thousands of Cursor licenses for non-engineers, with ~50% of their PRs accepted as-is, showing quality high enough to merge without endless developer patching.
- **Wrong approaches**: Giving developers bigger token limits on tasks they don't care about (leading to endless agent loops), giving PMs prototyping tools that just speed up the wait, and handing Claude Code to non-technical staff who then pester devs for environment setup.
- **Right approaches**: Use tools tuned for non-technical users (e.g., Autonomy AI's "Timely"), keep engineering guards in place, and maintain a "line in the sand" where engineers own architecture/backend and non-technical users own user-facing UX work.
- **The harness is essential**: Coined by Shun Hashimoto, a harness makes it unfeasible for an agent to repeat a mistake—providing automatic feedback that grows and adapts with usage.
- **Measure three things**: Count of PRs by non-technical individuals, merge rate (~74% is healthy, meaning 1 in 4 oversteps but trust is maintained), and zero-dev-touch merge rate (~84%, ensuring dev burden isn't increasing).
- **Failure is expected and healthy**: A 1,000-line PR that a developer correctly rejected (agent stored images server-side with no persistence plan) sparked a quick architectural conversation and the feature shipped a week later with the frontend reused.

## Detailed Breakdown

### Introduction and the Problem with AI Spend [00:00](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=0s)
Dubnov opens with a humorous framing—PMs writing code as a "horror story"—and quickly pivots to the real topic: organizations want to become AI native but struggle to define or measure it. He notes that many leaders face awkward CFO conversations about AI spending with no clear link to faster feature delivery.

### What "AI Native" Really Means [02:05](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=125s)
Everybody wants to be AI native, but almost nobody can define it. Dubnov offers his definition: AI native means the person who cares about a decision and has the authority to make it can also execute it. AI collapses the handover gap. The bottleneck hasn't been code-writing speed for a while—it's the multi-sprint handoff between PM, designer, and developer. When the person who cares can execute with agents, iterations that took days or weeks collapse to minutes.

### Everybody Gets an Upgrade [04:42](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=282s)
In an AI-native org, each role focuses on what it actually cares about. PMs stop writing specs nobody reads and instead directly implement and tune features. Engineers shift away from pixel-perfect UI work toward system architecture, refactoring, and dependencies. Senior engineers tackle harder problems. Hiring data reflects this: PM hiring is rising faster than developer hiring because decision-makers are now the bottleneck.

### Cautionary Tales: Uber and Microsoft [05:46](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=346s)
Uber increased AI spend 6x since 2024 and exhausted the entire budget in four months. Business leaders couldn't link the spend to faster feature delivery. Microsoft gave everyone Claude Code and is now taking it back—just handing AI tools to more people is a great way to burn money without speeding up the organization.

### Where the Token Budget Goes [07:19](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=439s)
An analysis of 2,400 companies shows that of every $100 spent on AI, only $18 goes to meaningful shipped code. The rest is consumed by rework, AI-generated bugs, and looping agents—a cycle driven by LLM provider economics and disengaged developers letting agents spin endlessly on tasks they don't care about.

### Shopify as a Positive Example [07:51](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=471s)
Shopify went all-in with thousands of Cursor licenses for non-engineers. Roughly 50% of PRs from non-technical contributors are accepted as-is, indicating quality high enough to merge without developer patching. Their VP of Engineering noted the fastest-growing groups are non-engineers who can now directly impact the product.

### Wrong Ways to Become AI Native [08:52](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=532s)
Three common mistakes: (1) Giving developers bigger token limits on the same uninteresting tasks—disinterested engineers let agents loop endlessly, burning tokens. (2) Giving PMs prototyping tools so they create Figmas faster, only to wait longer for devs—"hurry up and wait." (3) Giving Claude Code to PMs and designers who then constantly ask devs for environment help and open massive nonsense PRs, increasing PR fatigue.

### Right Ways and the Harness [10:24](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=624s)
Use tools tuned for the user type—Claude Code for developers, tools like Autonomy AI's "Timely" for non-technical individuals. Move the person who cares to the person who does the work. Don't let go of engineering guards. Dubnov references the "harness" concept (defined by Shun Hashimoto): when you see an agent make a mistake, you make it unfeasible to repeat. The harness must adapt and grow organically with usage.

### Harness Engineering Principles [12:59](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=779s)
Agents must understand and onboard themselves to the codebase without developer hand-holding. They need to communicate in product-level language, manage long sessions with fresh context, check their own work, know what "good" means, and learn across all users in parallel for exponential improvement. When working with non-technical users, the agent must own and read the code—translating code constraints to product language every time is impractical.

### Feasibility and the Line in the Sand [14:31](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=871s)
Dubnov addresses the "my codebase is a snowflake" objection: they've never encountered a setup they couldn't manage, from monorepos to NX to multi-repo with sibling libraries and private artifactory access. However, there's a line—engineers own architecture, DB, and backend decisions; non-technical users own user-facing UX work. Knowing where backend involvement starts is hard for non-technical contributors, and failure is expected.

### A Real PR Failure Example [16:33](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=993s)
A PM opened a ~1,000-line PR for an image-versioning feature. Product review passed beautifully, but the developer rejected it: the agent had stored images server-side with no persistence, so they'd vanish the next day. The developer team discussed storage architecture the next day, reused all the frontend/UX work, and shipped the feature a week later. The rejection was healthy—it accelerated a necessary conversation.

### How to Measure AI-Native Adoption [17:57](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=1077s)
Three metrics across hundreds of orgs and thousands of PRs: (1) **PR count** by non-technical individuals, tracked by person to ensure everyone is enabled. (2) **Merge rate**—their average non-technical contributor opens ~50 PRs per quarter with a 74% merge rate, meaning 1 in 4 oversteps but trust is maintained. (3) **Zero-dev-touch merge rate**—84% of merged PRs from non-technical users are merged without developers pushing additional commits, confirming dev burden isn't increasing.

### Q&A: Metrics Tooling [20:45](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=1245s)
Asked whether they use off-the-shelf tools for metrics, Dubnov explains Autonomy AI tracks this internally: the author appears as the Autonomy AI bot but traces back to the user, and they examine commit history before merge to detect whether anyone else pushed code changes (not just rebasing/merging).

### Q&A: Engineers Moving Toward PM/UX [21:49](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=1309s)
Dubnov describes their "plan, merge, polish" (PUMP) process. Developers are encouraged to make product/UX decisions themselves and merge quickly using feature flags. PMs, designers, and QA then open follow-up PRs to clean up. They're comfortable with a feature spanning three or four PRs.

### Q&A: Rollback Mechanisms [23:23](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=1403s)
Rollbacks depend on the organization's existing CI practices. The agent models the codebase deeply and writes the way the org writes—if they use feature flags, the agent outputs feature flags; if they don't write tests, the agent won't add them. The harness is intentionally non-opinionated and adapts to existing practices.

### Q&A: Visualizing PR Fatigue [24:26](https://www.youtube.com/watch?v=KzhjnILSP0Y&t=1466s)
Dubnov acknowledges the challenge. Autonomy AI optimizes agents to output minimal code by maximizing component reuse, which shrinks PRs. They also built an agent that labels every PR with risk level and size, so developers see "three small/low-risk, two medium, one extra-large" instead of an undifferentiated wall of nine PRs. Team leads factor this load data into review assignments to spread burden.
