# Harness Engineering: Building an AI Software Factory

## TL;DR
Dru, Head of Product and Design at Tessl, presents "harness engineering" (also called loop engineering or software factories) as the next evolution of AI-assisted development. The approach shifts engineers' focus from writing and correcting code to building and monitoring automated loops—inner, outer, and meta—that enable AI agents to autonomously produce, review, and improve software with higher velocity and quality.

## Key Takeaways
- **Software factories** are systems where AI agent loops build the end product while humans focus on shaping tasks and improving the autonomy, automation, and quality of the system.
- Three key dimensions to track and optimize: **autonomy** (fewer human course corrections), **automation** (less oversight needed), and **quality** (better code, not just faster code).
- **Harness engineering** revolves around three loops: the **inner loop** (fast checks like unit tests and linters driving autonomy), the **outer loop** (slower, in-depth checks like agentic code review driving automation), and the **meta loop** (automated agents that monitor and improve the other loops).
- Moving from interactive agent sessions to an **issue-tracker-and-PR workflow** is the single most crucial unlock for scaling agent productivity and enabling harness engineering.
- The biggest barriers to harness engineering are **organizational**, not technical—it requires a different, sometimes uncomfortable way of working.
- Software factories can unlock **higher quality**, not just velocity, by scaling review effort and eliminating backlogs of known bugs.
- Engineers should spend their time on **architecture, system design, and improving agent guardrails**, rather than writing or correcting code directly.
- Greenfield projects benefit from type-safe languages with integrated toolchains (e.g., Rust) and establishing all three loops from the start.
- Tessl provides tools—skills registries, maintenance agents, verifiers, and cloud launch capabilities—to make harness engineering more seamless and fun.

### What Is a Software Factory? [03:15](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=195s)
A software factory is a system where agent loops build the entire shipped product. Humans shift to shaping tickets and tasks, then improving the autonomy, automation, and quality of the system. Dru defines three dimensions to track: **autonomy** (how many course corrections an agent needs), **automation** (how much oversight is required), and **quality** (is the product still good). He warns that a common rut is unlocking autonomy without automation—where agents can work independently but humans still review everything, creating a review bottleneck.

### Why Build a Software Factory? [06:24](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=384s)
Beyond velocity, Dru argues software factories unlock higher quality. Two main causes of low-quality software—incomplete review and known-but-unfixed bugs—are addressed by tireless agentic code review and massively increased capacity to fix issues. He cites companies like Intercom seeing fewer bugs escape review. Additional benefits include broader exploration (non-engineers shipping code) and engineers spending more time on architecture and system design—the fun parts of software engineering.

### The Three Loops: Inner, Outer, and Meta [12:14](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=734s)
- **Inner loop [12:14](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=734s):** Drives autonomy. Fast, cheap checks—unit tests, linters, manual verification. With agents, you can be far more pedantic; every agent mistake should become a check. Linting and test suites grow massively and should be periodically pruned.
- **Outer loop [14:23](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=863s):** Drives automation. Slower, in-depth checks that build confidence in a PR—agentic code review, building the product, clicking through it, taking screenshots. The goal is to reduce human review burden.
- **Meta loop [15:59](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=959s):** Runs the other loops on autopilot. Agents monitor CI checks, PR comments, and agent logs over time, then propose or make improvements (new linting rules, skills, tests). This is where engineers spend most of their time in a mature factory.

### Why Harness Engineering Is Hard [17:05](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=1025s)
The difficulty is almost exclusively organizational. The knowledge landscape changes constantly. Harness engineering feels like unplanned work—when an agent fails, you discard the PR and improve the harness rather than fixing the code directly, which feels like a slot machine. It's hard to justify spending time on "science" instead of shipping features. Additionally, poor legibility means teams don't realize they're hitting the same problems repeatedly.

### Key Components and Workflow Changes [19:11](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=1151s)
The single most important change: move from interactive agent sessions to an **issue-tracker-and-PR workflow**. Dru cites an OpenAI white paper showing a 5x productivity increase from this shift. It forces better upfront task definition, creates legible surfaces for meta-loop agents to learn from, and eliminates the pain of reverting work—you just leave PR comments. Other components include a **skills registry** (like npm for agent skills), **agentifying services** (removing human-only login dependencies), a **company brain** (access to Slack, Notion, docs), and **cloud environments** for agents to run in.

### Improvement Loops and Maintenance Agents [25:00](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=1500s)
The final piece is automated improvement loops. Maintenance agents review the previous day's agent logs, issues, PR comments, and CI checks, then propose fixes or put up PRs. Low-risk PRs can be auto-merged; production code gets human review. The goal is to wake up to 2–3 reasonable PRs that just need approval, letting engineers focus on customer-facing features.

### How Tessl Helps [26:35](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=1595s)
Tessl positions itself as a platform for building software factories. It is batteries-included (capturing evolving best practices), open and modular (skills are standard files in your repo), and built around incremental adoption. Features include a skills/plugin registry with quality review and security checks, default integrations with Linear and GitHub, out-of-the-box code review tools, and the Tessl agent for discovering automatable work and running coding agents in the cloud.

### Metrics to Drive [31:50](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=1910s)
Dru recommends tracking and driving down manual takeovers (human PR comments, manual ticket decomposition), driving up agent-initiated PRs, and improving code quality. He advises not trying to do everything at once—first establish how to measure quality, then aspire to raise it rather than merely maintaining it.

### Q&A: Auto-Merging, Culture, and PR Scope [33:35](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=2015s)
Currently, Tessl still reviews all production PRs but allows auto-merge in safe areas (docs, test libraries, agent harnesses). A "change risk analyzer" evaluates PRs against team-defined policies to determine if human review is needed. On culture, Dru acknowledges communication is now the biggest bottleneck at Tessl (30% more PRs weekly for 3–4 weeks straight). Stopgaps include a weekly one-hour team sync. On large PRs, codifying that small, contained PRs auto-merge can incentivize better behavior. Tessl reviews ~700 PRs/week across ~24 engineers, with heavy agent review handling low-hanging fruit before human review.

### Q&A: Company Brain, Greenfield, and Differentiation [42:39](https://www.youtube.com/watch?v=bUtAGFXPc3A&t=2559s)
On the "company brain," Dru recommends testing what's useful via evals—raw sources like Granola transcripts and Slack are high bang-for-buck; Notion is useful but goes stale fast. For greenfield projects, he recommends type-safe languages with integrated toolchains (Rust, Elixir) and establishing all three loops from the start. On code review differentiation, Tessl uses "verifiers"—small, cheap, fast LLM-powered linting rules—shifting checks left and reducing cost from ~$25/PR to ~$0.30/day. Everything is integrated into the broader platform with a shared registry.
