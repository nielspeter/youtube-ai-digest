# Agents Write 95% of Our Code. Here's the Catch

## TL;DR
Amy Heineike explores the emergence of the "harness engineer"—a new role focused on building guardrails, invariants, and analytical feedback loops around AI coding agents. While agents now generate the vast majority of code at Tessl (over 90%), they frequently ignore instructions, introduce bugs, and require increasingly sophisticated systems of deterministic checks, skills, and risk-based review policies to keep codebases healthy.

## Key Takeaways
- AI coding tool adoption has surged, with the majority of code in many organizations now AI-authored, but bugs and incidents have jumped correspondingly.
- Benchmarks for isolated tasks are saturated, but long-running, multi-step agent tasks (e.g., Slop Code Bench) reveal dramatically lower success rates.
- Better models are far more expensive—there's roughly a 10x cost difference between mid-tier and frontier models—making cost-awareness critical at scale.
- Tessl's skills benchmark showed that while skills can steer agents effectively, only about 70% of instructions within skills are followed on average.
- Three core skill sets define the "harness engineer": systems thinking, analytics, and risk/operations reasoning.
- Invariants—design systems, architectural rules, naming conventions, library opinions—must be made explicit and enforced via CI gates, linters (like ast-grep), verifiers, and agentic code review.
- Analytics on agent logs, PR comments, code complexity, and mutation testing provide signals to identify recurring problems and form new guardrails.
- Risk policies need to become fine-grained: some parts of a codebase can auto-merge, while high-leverage areas require human review.
- At Tessl, over 90% of code now flows through an internal "software factory" with orchestrators, skills, deterministic checks, and triage gating.
- Practical starting steps: define invariants for your codebase, turn at least one into a CI gate, and use agents to summarize the last 50 PRs for recurring issues.

## Detailed Breakdown

### The Current State of AI Coding [00:00](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=0s)
Amy opens by acknowledging the paradox of the current moment: agents are simultaneously amazing and terrible. They generate enormous volumes of code, but their behavior is often opaque and unreliable, making code review and guardrail processes more critical than ever.

### Agent Adoption and Benchmark Saturation [01:33](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=93s)
Citing a Faros report, Amy highlights that AI coding tool adoption has moved from spiky to near-ubiquitous, with the majority of code in many organizations now AI-authored. Task-driven benchmarks are essentially saturated—agents can complete most definable tasks—but this doesn't mean the code is maintainable or healthy over time.

### Bugs, Incidents, and Slop Code Bench [02:39](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=159s)
The same Faros report shows a sharp jump in bugs and incidents, which resonates with a general sense that software feels "crunchier" lately. Amy introduces Slop Code Bench, a benchmark where agents must perform tasks in an unknown order over time, revealing much lower success rates and exposing agents' struggles with long-running, incremental work.

### The Cost-Intelligence Frontier [03:44](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=224s)
Amy presents a chart plotting agent cost against intelligence score. The price axis is logarithmic, revealing roughly a 100x difference between the cheapest and most expensive models, and a 10x difference between mid-tier and frontier models. Even when a better model can solve a problem, it may be prohibitively expensive at scale—Tessl alone saw 600 PRs closed in a single week.

### Skills Benchmark and Instruction Following [05:22](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=322s)
Tessl built a benchmark using 1,000 skills from open-source repos, creating tasks to compare agent performance with and without skills. While skills dramatically improve task success and allow cheaper models to perform well, only about 70% of instructions within skills are followed on average. There's wide variance across models and domains—agents often ignore instructions they would have followed anyway, or fail to adapt to new directives.

### The Steering Problem [07:29](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=449s)
Amy suggests that AI labs may be over-rotating on task completion and under-rotating on steering—the ability to get agents to follow specific instructions and work the way you want. This gap is what engineers feel when trying to control agent behavior, and it underscores the need for more robust review and guardrail processes.

### Engineering Matters More, Not Less [08:34](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=514s)
Rather than making engineering obsolete, agents make engineering practices more important. Knowledge that was previously tacit—shared through peer review, mentoring, and code ownership—must now be made explicit and encoded into systems that can survive agent-generated code.

### Systems Thinking and Invariants [09:38](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=578s)
The first key skill of the harness engineer is systems thinking: identifying invariants that should always hold true across a codebase. Examples include design systems, architectural rules, library opinions, error-surfacing practices, and naming conventions. Previously these lived in a code owner's head; now they must be captured as prompts, skills, or deterministic rules.

### Enforcing Patterns [11:50](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=710s)
Amy describes multiple enforcement layers: skills loaded at the right time, deterministic CI checks (highlighting ast-grep as a newly popular tool), narrow "verifiers" run per-file by quick agents, and broader agentic code review. Models are getting better at judging code against clear criteria, making agentic review increasingly powerful.

### Analytics as a Core Skill [14:29](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=869s)
The second skill is analytics. As code generation automates, it produces rich data—agent logs, PR comments, complexity analysis, mutation testing—that can reveal where agents waste time, repeatedly err, or create spaghetti architecture. Amy shares an example where agents were consistently confused by the Linear API, prompting the team to write a simple CLI wrapper. These signals feed back into hypotheses and new guardrails.

### Risk and Operations [17:06](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=1026s)
The third skill is risk and operations reasoning. Amy describes a tiered risk ladder at Tessl: research code is a free-for-all, internal tooling auto-merges with no human review, feature code requires engineer sign-off, and high-leverage areas require consultation with experienced team members. These policies must be codified into GitHub settings and CI checks.

### The Harness Engineer Role [19:14](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=1154s)
Amy synthesizes the three skills into the "harness engineer" role—someone who thinks about invariants, analytics, and risk policies. Some organizations will have dedicated harness engineers; for others, these tasks will become a growing part of every engineer's day. The metaphor shifts from builder to "tender and gardener" of the codebase.

### The Tessl Software Factory [19:47](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=1187s)
Tessl's internal software factory now processes over 90% of their code. The vision involves remote execution environments loaded with skills, context, deterministic checks, verifiers, automated code review, and triage gating. Update loops continuously monitor and improve each layer. Amy invites the audience to try the Tessl CLI and Tessl agent.

### Getting Started [21:22](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=1282s)
For engineers not doing this full-time, Amy recommends three starting exercises: define invariants for your codebase (uncomfortable but valuable), turn at least one into a CI gate and observe how often it fires, and ask an agent to summarize the last 50 PRs in your repo to identify recurring errors, repeated review comments, and CI failures.

### Q&A: Software Factory Workflow [22:54](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=1374s)
Amy explains that the factory's input is a Linear ticket, created via skills that define how much detail to include and when to push back. Tickets can originate from agent exploration sessions in tools like Conductor, or via a Slack bot ("@Dark Factory app") that reads a thread and creates a ticket. An orchestrator then picks up tickets and pushes them through the factory pipeline.

### Q&A: Preventing Contradictions and Agent Loops [24:30](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=1470s)
Addressing the risk of agents contradicting each other or modifying skills in conflicting ways, Amy emphasizes that no agent output should be treated as authoritative. Coding agents should be prompted to "consider" findings rather than blindly "fix all issues." She also recommends treating the system as data—monitoring comment distributions, experimenting with prompts, and applying the scientific method to identify and resolve hang-ups.

### Q&A: Skills, Cost Reduction, and Instruction Adherence [27:06](https://www.youtube.com/watch?v=g_iDPqIRvfI&t=1626s)
Amy clarifies that the 70% instruction-following figure refers to individual instructions within skills. Problems include agents ignoring skills entirely (often a description/loading issue), overly prescriptive skills that overwhelm agents, and contradictory skills that cause agents to give up. Tessl offers a "Tessl Review" feature to help evaluate skill descriptions. Amy notes that some agent behaviors remain mysterious—"it's a bunch of numbers in a massive matrix."
