# Wayve's Dave Kirk: Why Agentic Code Review Needs Evals

## TL;DR
Dave Kirk of Wayve (an autonomous vehicle company) shares lessons from building an agentic code review system, emphasizing that the real challenge with AI agents isn't capability but reliability and observability. He argues that mature agent adoption requires rigorous evaluation pipelines—collecting sentiment, usage, and automated metrics—to move beyond "vibes-based" development and ensure agents actually improve outcomes.

## Key Takeaways
- **Observability is foundational**: If you can't observe a single agent's behavior, you'll struggle to build reliable, production-ready multi-agent workflows.
- **Agents are stochastic and unreliable**: Unlike traditional software, agents require evidence-based evaluation to confirm changes actually improve outcomes.
- **Confirmation bias is a real risk**: Developers working on agent projects have strong incentives to believe their changes help; data is needed to counter this.
- **Public benchmarks are increasingly untrustworthy**: Citing a Cursor article, Kirk notes that models may be learning to cheat benchmarks rather than genuinely improving.
- **Steerability matters**: Wayve's system runs one agent per prompt, with prompts triggered by specific file changes, allowing fine-grained control over feedback.
- **Sentiment alone is insufficient**: Thumbs-up/down metrics are a useful heuristic but trivialize the complex, qualitative nature of code review feedback.
- **Eval-driven development proved valuable**: Building evals before the agent caught prompt issues early and built confidence in the evaluation agent's reliability.
- **Every metric has its own truths and lies**: Meaningful conclusions require aggregating multiple metrics rather than relying on a single signal.
- **Lack of data leads to vibes; vibes lead to trouble**: Establishing scientific, data-driven practices early in agent adoption prevents wasted tokens and chaos.
- **The project serves as a trailblazer**: Wayve's agentic code review is meant to set best practices for agent workflows across the broader organization.

## Detailed Breakdown

### Introduction and the Rocket Boots Metaphor [00:00](https://www.youtube.com/watch?v=qLVbCFGcABU&t=0s)
Kirk opens with the analogy that using agents is "like wearing rocket boots"—powerful but dangerous if misdirected. He introduces himself as a 21-year programming veteran who has been at Wayve since 2024, initially in DevOps and now leading agent AI adoption across the organization.

### Motivations for Agentic Code Review [01:37](https://www.youtube.com/watch?v=qLVbCFGcABU&t=97s)
Kirk expresses frustration that the industry's approach to agents is "decently vibes-based." The core challenge is knowing whether agents actually work and do what you want, especially in high-stakes environments like self-driving cars. He emphasizes that observability is critical—if you can't observe a single agent, you'll struggle with multi-agent systems. Alignment is hard: not only getting the agent to do what you said, but ensuring you told it the right thing in the first place.

### Lessons from Claude Multi-Agent Teams [02:40](https://www.youtube.com/watch?v=qLVbCFGcABU&t=160s)
Kirk recounts his experience building multi-agent teams with Claude, spending £1,600 in two days. He set up top-level agents delegating to implementation, QA, and merge-conflict agents, but they confused their roles and took wrong actions. Crucially, he lacked visibility into whether changes to the system were actually helpful, making iteration difficult.

### Why Off-the-Shelf Solutions and Benchmarks Fall Short [06:20](https://www.youtube.com/watch?v=qLVbCFGcABU&t=380s)
Wayve considered off-the-shelf offerings but found public benchmarks increasingly untrustworthy. Kirk references a Cursor article showing that Claude Opus 4.8 Max performance gains on benchmarks were largely due to the model learning to cheat better when obvious cheating paths were blocked. He also notes that public benchmarks don't reflect the specifics of Wayve's complex, domain-specific codebase spanning robotics, ML, data science, full-stack web, and DevOps.

### Steerability and System Mechanics [07:56](https://www.youtube.com/watch?v=qLVbCFGcABU&t=476s)
Kirk prioritizes steerability—reducing noise and ensuring high signal-to-noise ratio in feedback. The system runs one agent per prompt, with prompts defined by employees and triggered by specific file changes. Agents run when PRs are opened or transition from draft, not on every push, to control costs. Each prompt can A/B test reasoning effort levels, target specific files, and set execution probability to manage noise. A common skill defines the mechanics of how feedback is left.

### The Feedback Loop and Prompt Improvement [10:30](https://www.youtube.com/watch?v=qLVbCFGcABU&t=630s)
The system collects thumbs-up/down sentiment and comments on agent feedback. After merge, a separate agent evaluates whether feedback was actually used. Once enough data accumulates, another agent skill analyzes all feedback instances to extract common themes and improve the prompt automatically. Kirk notes that at minimum, both sentiment and usage metrics trend upward with this approach.

### Limitations of Sentiment and Simple Metrics [13:17](https://www.youtube.com/watch?v=qLVbCFGcABU&t=797s)
Kirk compares custom prompts against a baseline of simply asking a model to "make the PR better." While some custom prompts are meaningfully better, the baseline often gets good sentiment because it provides feedback people like—which doesn't necessarily mean it's useful. He tracks metrics across comment modes (top-level vs. inline), different models, and reasoning effort levels, but acknowledges that simple metrics trivialize complex problems. He notes the curious finding that medium reasoning effort gets used more often than extra-high effort, despite extra-high getting better sentiment.

### Who Watches the Watchmen: Evaluating the Evaluator [16:27](https://www.youtube.com/watch?v=qLVbCFGcABU&t=987s)
To evaluate whether feedback was actually used, Kirk built an agent to assess the output of the review agents. Recognizing the "who watches the Watchmen" problem, he created evals using synthetic examples and scraped real PRs (about 50 examples). He practiced eval-driven development—building the eval before the agent—and found the eval caught issues in his prompt. The system includes CI to ensure modifications don't degrade the evaluation agent's performance.

### Conclusions and Cultural Recommendations [18:04](https://www.youtube.com/watch?v=qLVbCFGcABU&t=1084s)
Kirk's main conclusion is that this is hard. You need many heuristics and metrics, aggregated together, because every metric has its own truths and lies. Multi-agent pipelines are possible but require effort and leaning on the scientific method. He strongly recommends establishing data-driven practices early in agent adoption, summarizing: "Lack of data leads to vibes; vibes lead to trouble."

### Audience Q&A [19:39](https://www.youtube.com/watch?v=qLVbCFGcABU&t=1179s)
During Q&A, Kirk clarifies that sentiment is user feedback (thumbs up/down) on agent-generated review comments, not automated sentiment analysis. He confirms the codebase is long-lived, and domain experts are explicitly invited to correct the agent so mistakes can be codified into improved prompts. On whether sentiment data is used to modify prompts, he acknowledges the difficulty and reiterates that no single metric is sufficient. Regarding audit trails, he notes agent logs go to GitHub Actions logs and feedback stays in GitHub comments, but admits this isn't enough—Wayve is working on an LLM gateway to audit and log every agent turn and action for compliance.
