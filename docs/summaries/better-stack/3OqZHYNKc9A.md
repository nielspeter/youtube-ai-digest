# This Tiny Tool Fits a 744B AI Model on Normal Hardware (colibrì)

[![This Tiny Tool Fits a 744B AI Model on Normal Hardware (colibrì)](https://i.ytimg.com/vi/3OqZHYNKc9A/hqdefault.jpg)](https://www.youtube.com/watch?v=3OqZHYNKc9A)

## TL;DR
Colibri is a lightweight, pure-C inference engine by developer Vincenzo Fornaro that streams the 744B-parameter GLM 5.2 mixture-of-experts model from disk, letting you run frontier-scale AI on consumer hardware. Testing reveals that while the tool genuinely works, real-world speed depends almost entirely on system RAM and fast storage—not GPU power—with a beefy workstation achieving roughly 0.8 tokens/second versus a crawl on a RAM-constrained MacBook.

## Key Takeaways
- GLM 5.2 is a 744B-parameter mixture-of-experts model; only ~40B parameters (≈5%) are active per token, and the dense always-used components are just ~17B parameters.
- Colibri exploits this by keeping dense components in RAM while streaming individual experts from NVMe SSD on demand, caching the hottest ones.
- The engine is written in pure C with zero external dependencies, making it extremely lean.
- A learning cache records which experts your prompts route to and pins the most-used ones into spare RAM at startup, improving performance with repeated use.
- Colibri uses speculative decoding (native multi-token prediction) and compressed MLA attention (shrinking the KV cache ~57×) to reduce memory footprint and boost speed.
- The forward pass is validated to be token-exact against a reference transformers implementation, preserving output quality.
- On a MacBook M2 Max with 32 GB RAM and an external USB SSD, the model worked but took ~2 minutes to produce the first word at ~0.1 tokens/second; over 80% of time was spent waiting on disk.
- On a workstation with an RTX 5090, 64 GB RAM, and internal SSD, speed improved to ~0.8 tokens/second with first word in ~17 seconds; disk-wait time dropped to ~48%.
- The GPU was barely utilized—the single biggest bottleneck is system RAM and storage speed, not compute.
- Vincenzo's own benchmarks show the fastest usable configs are serious machines like a dual-Xeon server with 1 TB of RAM, reinforcing that memory is the key factor.

## Detailed Breakdown

### The Scale of the Challenge [00:00](https://www.youtube.com/watch?v=3OqZHYNKc9A&t=0s)
The video opens by introducing GLM 5.2, a 744-billion-parameter language model in the same size class as frontier data-center models. Developer Vincenzo Fornaro created Colibri, a tool that claims to run this model locally on consumer hardware. The host sets up the central question: how is this even possible, and does it actually work?

### Why Mixture-of-Experts Makes It Possible [01:03](https://www.youtube.com/watch?v=3OqZHYNKc9A&t=63s)
Running a 700B+ model normally requires fitting all weights into memory at once—hundreds of gigabytes even at INT4 quantization. GLM 5.2 is a mixture-of-experts (MoE) model: instead of one giant dense network, it contains thousands of smaller specialist sub-networks. For any given token, only a tiny fraction are activated—about 40B out of 744B parameters, roughly 5%. This gap between total size and active usage is what Colibri exploits.

### Colibri's Architecture and Memory Hierarchy [02:04](https://www.youtube.com/watch?v=3OqZHYNKc9A&t=124s)
Colibri treats the machine's storage as a layered memory hierarchy: GPU VRAM, system RAM, and NVMe SSD function like cache tiers. The dense components used on every token (~17B parameters, under 10 GB at INT4) stay resident in RAM permanently. The experts live on the SSD and are streamed on demand, then cached. The entire engine is written in pure C with zero external dependencies, which keeps it extremely lean.

### Fighting Slowdowns: Caching, Speculation, and Quality [03:06](https://www.youtube.com/watch?v=3OqZHYNKc9A&t=186s)
Colibri combats the inherent slowness of disk streaming with three tricks. First, a learning cache records which experts your prompts route to and pins the hottest ones into spare RAM at startup, so performance improves for repeated task types. Second, speculative decoding uses a native multi-token prediction head to generate faster than one token at a time. Third, the forward pass is validated to be token-exact against a reference transformers implementation, ensuring the quantized streaming version produces identical outputs to the full-precision reference. Additionally, compressed MLA attention shrinks the KV cache by about 57×.

### The Storage Space Problem [04:08](https://www.youtube.com/watch?v=3OqZHYNKc9A&t=248s)
The first practical hurdle is disk space: GLM 5.2 is about 357 GB. The host couldn't free enough internal space on the MacBook, so the model was placed on an external Samsung portable SSD with roughly 1 GB/s transfer speed. This decision proved consequential: USB external drives are significantly slower than internal drives (1 GB/s vs. 7+ GB/s), and since Colibri constantly streams model pieces off disk, a slow drive means slow everything.

### Test 1: MacBook M2 Max with External SSD [05:09](https://www.youtube.com/watch?v=3OqZHYNKc9A&t=309s)
The first test used a MacBook with an M2 Max chip, 32 GB of RAM, and the model on the external SSD. The prompt "What is the capital of Belgium?" produced a correct answer (Brussels), proving the tool works. However, the first word took over 2 minutes to appear, and generation crawled at about 0.1 tokens/second (roughly one word every 10 seconds). This was a cold start with nothing cached, and the Mac's limited RAM couldn't hold many experts after warming up.

### Profiling the MacBook Bottleneck [06:43](https://www.youtube.com/watch?v=3OqZHYNKc9A&t=403s)
Colibri's profiling screen revealed the breakdown: of ~158 seconds total, roughly 145 seconds (over 80%) was pure disk-waiting time. The actual math/compute took only about 7 seconds. The M2 Max CPU is fast—the problem is that the model doesn't fit in 32 GB of RAM, forcing constant trips to the slow external drive. The computer spent almost all its time waiting and barely any time computing.

### Test 2: Workstation with RTX 5090 and Internal SSD [07:45](https://www.youtube.com/watch?v=3OqZHYNKc9A&t=465s)
The second test used a beefy workstation with an RTX 5090, 64 GB of RAM, and the model on a fast internal drive with 350 GB of spare space. The prompt "Explain quantum entanglement in simple terms" produced a clean, useful explanation using a magical-coins analogy. Speed improved to about 0.8 tokens/second, with the first word appearing in ~17 seconds—roughly eight times faster than the Mac.

### Profiling the Workstation and the Real Bottleneck [08:18](https://www.youtube.com/watch?v=3OqZHYNKc9A&t=498s)
On the workstation, disk-waiting time dropped to about 48% (nearly halved), and real compute time became visible. Surprisingly, the RTX 5090 was barely breaking a sweat. The improvement came not from the GPU but from doubled RAM and a faster internal drive, allowing a much larger portion of the model to sit in memory. The single biggest factor holding these models back on consumer hardware is memory capacity, not GPU power—a rough conclusion given how expensive RAM has become.

### Verdict and Vincenzo's Benchmarks [09:52](https://www.youtube.com/watch?v=3OqZHYNKc9A&t=592s)
The host confirms: yes, you can run a 744B-parameter frontier model on consumer hardware—he did it twice with correct results. But running it and running it well are different things. Vincenzo's own benchmarks show the fastest usable configs are still serious machines, like a six-GPU rig or a dual-Xeon server with 1 TB of RAM. Notably, the 1 TB RAM server with no fancy GPU beats a single RTX 5090 by a mile, reinforcing that memory is the decisive factor. The dream of a frontier model on an average laptop isn't quite here yet, but it's very close.
